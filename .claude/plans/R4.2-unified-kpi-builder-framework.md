## 2. Frozen Product Decisions
- Existing submission, recommendation, and final verification flow stays unchanged.
- Existing `keyUnitId` and `finalUnitId` routing stays unchanged.
- Existing dashboards and notification architecture stay unchanged in this phase.
- Existing `Research Paper`, `Grant`, and `Patent` templates stay conceptually intact and become pluggable full KPI templates.
- Templates remain useful; blank-from-scratch KPI creation also stays available.
- Dynamic fields are first-class and tenant-configurable.
- Dynamic fields can drive validation, conditional visibility, conditional requiredness, tier rules, reward amount sources, and uniqueness/reward recurrence.
- Dynamic fields do not create roles. Roles remain a separate people/distribution construct.
- Roles are defined once at KPI level as the master role catalog.
- Tiers may override role usage for payout, but tiers do not create disconnected role universes.
- One contributor keeps one primary role on an achievement but may have extra reward selector tags such as `FIRST_AUTHOR` or `CORRESPONDING_AUTHOR`.
- Reward engine in this phase runs only after final verification.
- Stage definitions and evidence remain in scope, but stage-triggered reward release and final-settlement-on-stage logic are deferred.
- One tier is resolved per tier set. Default overlap policy is `HIGHEST_PRIORITY_WINS`.
- Builder warns on overlapping tier conditions before save.
- Tier rows support `effectiveFrom` and optional `effectiveTo`.
- Tier applicability is determined by achievement policy date, not submission or verification date.
- Policy date resolution is: use a KPI-bound policy-date field if configured, otherwise `achievement.actualDate`, otherwise `reportingDate`.
- Reward recurrence policy is configurable per KPI: `RECURRING`, `ONCE_PER_PERIOD`, `ONCE_PER_KPI_LIFETIME`, `ONCE_PER_UNIQUE_KEY`.
- `ONCE_PER_UNIQUE_KEY` uses configured duplicate-check bindings and is invalid unless at least one unique-bound field exists.
- Reward distribution is generic and component-based.
- If only one eligible contributor exists, default payout behavior is `FULL_TO_SINGLE`.
- If a configured share group is empty, default fallback is `ROLLOVER_TO_MATCHED`.
- Benefit precision and rounding are defined per `BenefitType`.
- Decimal residuals from pooled splitting are assigned to the lead selector by default.
- If a reward component has no explicit team distribution, default payout goes to one person using `DIRECT_OWNER`.
- Copy/import is same-tenant only.
- Copy/import is config-only and must never copy achievements, reward ledger rows, review history, notifications, or progress state.
- This framework is intended to cover 90-95% of real institutional KPI scenarios without future schema redesign.

## 3. Architecture and Storage Strategy
- Keep current models for KPI core, roles, stages, contributor config, achievements, contributors, benefit types, and external contributor templates.
- Add `KpiTemplate` as a full builder snapshot model.
- Add `KpiRewardTier`.
- Add `KpiRewardRule`.
- Add `KpiRewardComponent`.
- Add `KpiRewardDistribution`.
- Add `ContributorReward` as immutable reward ledger.
- Keep dynamic form definition JSON-backed in KPI/template.
- Keep achievement form answers JSON-backed in `Achievement`.
- Keep template snapshot payload JSON-backed.
- Keep operational reward logic relational.
- Keep reporting-critical reward outputs relational.
- Do not store core payout logic only in JSON.
- Continue using Postgres `JSONB` for dynamic configs and answers.
- Treat JSON as config/data-capture flexibility, not as the primary query layer for reward logic.

## 5. Reward Model Scope
- Reward amount modes in scope are `FIXED_VALUE`, `FIXED_POOL`, `FIXED_PER_PERSON`, `PERCENT_OF_FIELD`, `PER_UNIT`, and `PERCENT_OF_SCORE`.
- Reward distribution modes in scope are `DIRECT_OWNER`, `ROLE_PERCENT_SPLIT`, `FIXED_PER_PERSON`, `EQUAL_SPLIT`, `CREDIT_PERCENT_SPLIT`, and `LEAD_ONLY`.
- Tier rule sources in scope are form fields, `actualValue`, `computedScore`, `effectiveScore`, named system metrics, team size, and manual selection.
- Tier rule operators in scope are `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `contains`, `in`, `has_any`, `has_all`, `not_in`, and `not_contains`.
- Publication incentives must be supported as a reference scenario:
  - Q1/Q2/Q3/Q4 tiers
  - UGC care tier
  - first-author-led splits for quartile tiers
  - corresponding-author-led split for UGC tier
  - 70/30 role-plus-remainder distribution
  - single-author 100% fallback
  - monetary and points on the same tier
- No additive or differential tier stacking in this phase.
- No cross-KPI pooled budget engine in this phase.
- No retroactive repricing engine in this phase.
- No arbitrary scripting or custom formula language in this phase.

## 8. Checks and Balances During Development
- Do not begin a module until the previous module gate is green.
- Do not merge a module with unresolved schema ambiguities.
- Do not let new builder logic bypass tenant or admin permission checks.
- Do not let reward generation happen from UI preview calls.
- Do not let reward generation mutate past reward rows implicitly.
- Do not let field renames or deletions leave dangling tier-rule references or duplicate-check bindings.
- Do not let copied distributions exist without copied components.
- Do not let tier-linked components exist without copied tiers.
- Do not let `ONCE_PER_UNIQUE_KEY` KPIs save without a valid unique-bound field.
- Do not let overlapping tier rules save silently without warning.
- Do not let no-role KPIs force role setup.
- Do not let team KPIs assume reward distribution must follow credit percent.
- Do not let publication-style selector tags replace the contributor primary role; they are additive metadata only.
- Do not let builder-generated changes alter dashboards, routing, notifications, submission, recommendation, or verification semantics.
- Do not allow arbitrary code execution or free-form scripting in config.
- Always log template apply, copy/import, builder save, and reward generation actions to audit logs.
- Always validate same-tenant boundaries for copy/import, template use, and reward calculation.
