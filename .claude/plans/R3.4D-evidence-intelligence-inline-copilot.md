# R3.4D: Evidence Intelligence and Inline Accreditation Copilot UX

## Summary

Build the next accreditation module as the **evidence-grounding and inline review layer** for the copilot that already exists.

What is already in place:
- block-native scoring and dependency execution
- institutional data bank and source projection
- workspace reporting, readiness, DVV, and recommendation tracking
- body-configured copilot packs and LLM profile selection
- tenant-level superadmin feature gating for copilot

What is still missing:
- real understanding of accreditation evidence files
- evidence-to-claim citations that users can trust
- inline authoring and reviewer UX that fits daily accreditation work

This phase closes that gap.

Chosen defaults:
- support both deterministic fallback and LLM-assisted review
- keep official responses and scores deterministic and manually controlled
- start with **PDF/text/image evidence extraction**, not arbitrary document processing
- inline copilot is embedded into the existing workspace entry experience, not a separate AI page
- every AI review or draft must be grounded in block data, institutional metrics, evidence metadata, or extracted evidence chunks

Out of scope:
- public peer benchmarking and competitor intelligence
- full SSR / narrative document generation
- autonomous auto-filing or direct write-to-response behavior

## Why This Is Next

The current copilot stack is configurable and body-aware, but not yet strong enough for real accreditation teams to rely on during final drafting and review.

The largest remaining usability gap is:
- users attach evidence, but the assistant cannot deeply inspect much of it
- users receive suggestions, but cannot compare or apply them cleanly inside the editing flow
- reviewers still need stronger "why is this risky?" and "what supports this claim?" guidance

This phase should make the copilot operationally useful in real filing work.

## User Problems To Solve

The app should help users answer these specific questions while filling a block:
- What evidence in this workspace actually supports this response?
- Is the response making claims not backed by documents or metrics?
- Is the uploaded evidence stale, incomplete, scanned, unreadable, or low-confidence?
- Draft a stronger response using only what is already in the workspace.
- Show me the exact evidence snippets behind this suggestion.
- Highlight the difference between my current response and the assistant's proposed draft.
- Tell me what a reviewer or assessor is likely to challenge here.
- Let a reviewer leave AI-assisted comments without mutating the official response.

## Key Changes

### 1. Evidence extraction and indexing runtime

Extend the current `EvidenceVersionExtraction` model and processing pipeline into a real extraction system.

Default operating rules:
- extraction is **on-demand**, not automatic on every upload
- extraction may be triggered by:
  - explicit user action
  - lazy extraction during copilot use
  - coordinator bulk extraction
- identical content hashes should reuse one extraction result wherever allowed
- default tenant extracted-text storage budget: `500MB`
- warn at `80%` extracted-text capacity
- default concurrent extraction cap: `5` active jobs per tenant
- extracted derivatives for `ARCHIVED` workspaces may be garbage-collected after a configurable retention window
- original evidence files are never deleted by extraction cleanup

Required capabilities:
- text extraction from:
  - PDF documents
  - plain text files
  - DOCX-like text sources where feasible
- OCR for image-based and scanned evidence
- table-aware extraction for evidence with row/column structure
- chunking and normalization for long extracted content
- evidence extraction status and quality scoring

Suggested extraction states:
- `PENDING`
- `PROCESSING`
- `READY`
- `PARTIAL`
- `FAILED`
- `STALE`

Suggested extraction quality flags:
- `TEXT_NATIVE`
- `OCR_USED`
- `LOW_CONFIDENCE`
- `TABLES_DETECTED`
- `TABLES_PARTIAL`
- `UNSUPPORTED_FORMAT`
- `TOO_LARGE`
- `PASSWORD_PROTECTED`

Every extraction should persist:
- content hash of the source file version
- extraction engine version
- language hints
- extraction text and chunk boundaries
- structured table segments where available
- quality flags
- confidence score or confidence band

Extraction versioning rules:
- `engineVersion` must be explicit on `EvidenceVersionExtraction`
- when the extraction engine changes, old extractions are marked `STALE`, not silently replaced
- re-extraction happens on-demand on next use or explicit user action
- existing suggestions grounded on stale extractions must be marked stale with a machine-readable reason such as `extraction_engine_upgraded`
- keep at most two active extraction-engine generations before forcing re-extraction on access

### 2. Evidence chunk model and citation mapping

Add a dedicated chunk/citation layer so suggestions can cite exact evidence locations.

Concrete schema targets:

```prisma
model EvidenceVersionChunk {
  id             String                   @id @default(cuid())
  extractionId   String
  chunkIndex     Int
  pageStart      Int?
  pageEnd        Int?
  sectionHeading String?
  contentType    String                   @default("TEXT")
  plainText      String                   @db.Text
  charCount      Int
  tokenEstimate  Int?
  confidence     Float?
  metadata       Json?
  createdAt      DateTime                 @default(now())
  extraction     EvidenceVersionExtraction @relation(fields: [extractionId], references: [id], onDelete: Cascade)

  @@index([extractionId, chunkIndex])
  @@index([extractionId, contentType])
}
```

```prisma
model EvidenceSuggestionCitation {
  id                String   @id @default(cuid())
  suggestionId      String
  citationType      String
  evidenceVersionId String?
  chunkId           String?
  metricCode        String?
  responseFieldKey  String?
  renderedSnippet   String?  @db.Text
  confidence        Float?
  createdAt         DateTime @default(now())
  suggestion        AccreditationAssistantSuggestion @relation(fields: [suggestionId], references: [id], onDelete: Cascade)

  @@index([suggestionId])
  @@index([evidenceVersionId])
  @@index([chunkId])
}
```

Chunking defaults:
- target chunk size: about `800` tokens
- boundary overlap: about `100` tokens
- split order: heading -> paragraph -> sentence -> never mid-word
- minimum chunk size: about `50` tokens
- hard maximum chunk size: about `2500` tokens
- tables remain atomic unless they exceed the hard maximum, then split only at row boundaries
- chunking must be deterministic for the same content hash plus engine version

Goal:
- every grounded assistant output can point to exact supporting chunks
- the UI can render evidence-backed citations, not generic "source used"

### 3. Evidence relevance and grounding builder

Refactor grounding so it does not send the full workspace blindly into prompts.

Build an evidence relevance layer that selects chunks using:
- block id / block type
- evidence link relationship to the block
- evidence schema expectations
- body-version assistant pack
- metric aliases referenced in the block
- response text keywords and structured fields
- extracted table headings and page metadata

Grounding priority:
1. current block response and structured response fields
2. institutional metrics projected into the block
3. evidence directly linked to the block
4. evidence indirectly linked at workspace level
5. readiness/completeness/evidence-gap context

Default prompt-budget targets:

| Action | Input Budget | Output Budget | Evidence Budget |
|---|---:|---:|---:|
| Explain | 3K | 800 | ~2 chunks |
| Review | 6K | 1.5K | ~4 chunks |
| Draft | 8K | 2.5K | ~6 chunks |
| Watchlist | 8K | 2K | none or minimal |
| Question Checklist | 4K | 1K | ~2 chunks |

Evidence ranking strategy:
1. directly linked evidence for the active block
2. evidence whose type matches the block evidence schema
3. chunks matching block title, response fields, or metric aliases
4. workspace-level evidence only if direct evidence is insufficient

Grounding fallback contract:

| Evidence State | Copilot Behavior | groundingStatus |
|---|---|---|
| extraction ready with usable chunks | full grounded response with chunk citations | `FULLY_GROUNDED` |
| extraction partial | grounded response with incomplete coverage warning | `PARTIALLY_GROUNDED` |
| extraction failed or unreadable | metadata-only review with explicit warning | `METADATA_ONLY` |
| extraction pending | lazy extraction or metadata-only fallback with extract CTA | `METADATA_ONLY` |
| no evidence linked | response + metrics only, with attach-evidence warning | `NO_EVIDENCE` |

Important rules:
- if high-confidence grounding cannot be assembled, the assistant must explicitly degrade rather than pretend full review quality
- if chunks exceed budget, include highest-ranked chunks and explicitly state that more evidence was available than could fit
- prompt building must remain deterministic enough that repeated runs with unchanged content choose the same ranked chunk set where feasible

### 4. Inline authoring UX

Add inline copilot flows inside the block-entry experience.

Core UX:
- `Explain`
  - criterion meaning
  - expected evidence
  - what good responses usually contain for the active body/version
- `Review`
  - unsupported claims
  - stale data usage
  - missing required evidence
  - likely assessor challenge points
- `Draft`
  - produces a proposed draft from current response + metrics + evidence
- `Question Checklist`
  - likely questions reviewer / DVV / peer team may ask

Inline actions:
- `Compare`
  - current response vs suggested response
  - sentence/paragraph-level diff
- `Apply to Draft`
  - copies suggestion into editor draft state only
  - does not auto-save official response
- `Insert Citation Reference`
  - allows inserting a selected evidence citation into the local draft
- `Dismiss` / `Mark Useful`
  - feedback loop on suggestion quality

Feedback capture should be explicit on `AccreditationAssistantSuggestion`:
- `feedbackRating Int?`
- `feedbackNote String?`
- `feedbackByUserId String?`
- `feedbackAt DateTime?`

Optional analytics surface:
- average rating by suggestion type
- average rating by body/version pack
- most-dismissed suggestion patterns
- blocks with consistently low-rated suggestions

### 5. Reviewer-mode copilot

Add a reviewer-specific mode that does not behave like a drafting assistant.

Reviewer mode should focus on:
- claim-evidence mismatch detection
- weak or repetitive narrative warnings
- cross-field inconsistencies in the same block
- year coverage gaps
- missing final evidence version
- stale projections or outdated institutional metrics
- block-level risk severity and recommended next action

Use one unified suggestion contract across the copilot stack:

```prisma
enum SuggestionType {
  GUIDANCE
  DRAFT
  RISK_ASSESSMENT
  QUESTION_CHECKLIST
  REVIEW_CONTENT
  REVIEW_EVIDENCE
  REVIEW_COMMENT
}
```

Recommended usage:
- author-facing explain -> `GUIDANCE`
- author-facing draft -> `DRAFT`
- author-facing or reviewer risk summary -> `RISK_ASSESSMENT`
- reviewer critique of response quality -> `REVIEW_CONTENT`
- reviewer critique of evidence sufficiency or stale proofs -> `REVIEW_EVIDENCE`
- reviewer-specific free-form observation -> `REVIEW_COMMENT`

### 6. Body-aware review heuristics on top of evidence

Use the existing body/version assistant hierarchy, but now connect it to evidence review.

Body/version packs should be able to define:
- preferred evidence classes
- evidence sufficiency rules
- minimum narrative coverage expectations
- disallowed claims without quantitative proof
- narrative style expectations for institution-level vs program-level accreditations
- expected treatment of missing, zero, estimated, and not-applicable values

Block-level `assistantConfig` should refine:
- evidence emphasis
- review severity
- whether table evidence is critical
- whether metric parity with narrative claims is required

### 7. Suggestion lifecycle and staleness

Existing suggestion rows must become truly lifecycle-aware.

Suggestions should become `STALE` when any of these change:
- current block response
- evidence link set for the block
- evidence version content hash
- extraction version or extracted chunk set
- projected institutional metric values used by the suggestion

Additional stale reasons should be explicit:
- `response_changed`
- `evidence_changed`
- `extraction_engine_upgraded`
- `metric_input_changed`
- `citation_orphaned`

Chunk replacement rules:
- when re-extraction replaces old chunks, old chunk references may become invalid
- orphaned evidence citations should automatically stale the suggestion rather than silently degrade it
- new copilot calls should always produce fresh citations against the current extraction set

Do not silently reuse stale suggestions as if they were current.

### 8. Safety, privacy, and anti-injection controls

Non-negotiable rules:
- extracted evidence text is untrusted content, not instruction authority
- prompt building must isolate system instructions from retrieved evidence text
- unrelated workspace evidence must not be sent to the model
- redact or omit PII-heavy fields unless the active assistant pack explicitly needs them
- frozen workspaces may allow review and explain, but must not allow apply-to-draft actions
- unsupported or low-confidence extraction must degrade gracefully to metadata-only review

## Edge Cases and Failure Modes

This phase must explicitly handle:

- scanned PDFs with no embedded text
- OCR success but low confidence
- evidence with large tables that are only partially extractable
- password-protected or corrupted files
- multiple evidence versions linked to the same block, including outdated finals
- evidence linked at workspace level but not block level
- evidence attached but extraction missing or stale
- extraction pending while review is requested
- huge evidence sets that exceed context limits
- duplicate evidence files with different names but same content hash
- conflicting evidence sources inside the same block
- response claims that contradict projected metrics
- response claims using zero where the metric semantics say "missing"
- `NOT_APPLICABLE` metric semantics being incorrectly treated as a gap
- same evidence reused across multiple blocks with different framing requirements
- program-level accreditation using institution-level evidence that is too broad
- frozen workspaces where explain/review are allowed but apply-to-draft is forbidden
- unsupported file types
- extraction engine version upgrades invalidating prior chunk references
- malicious prompt injection text inside evidence files
- multilingual evidence where extraction language is mixed or uncertain
- per-tenant extraction storage limits or concurrent extraction queue saturation

## Test Plan

### Extraction and storage
- native-text PDF extraction stores chunks and page references
- scanned image/PDF routes through OCR and records lower confidence when appropriate
- unsupported or failed extraction is stored with explicit failure state
- extraction re-run on changed file version invalidates prior chunk grounding
- duplicate file content hashes avoid redundant extraction where allowed
- chunking is deterministic for the same content hash plus engine version
- archived workspace extraction cleanup affects only derivative extraction data, never source evidence files
- concurrent extraction throttling queues excess jobs rather than failing unpredictably

### Copilot grounding
- explain/review/draft use only relevant block-linked evidence and current block context
- insufficient grounding returns explicit degraded result
- table-derived citations resolve to extracted table segments
- stale suggestions are marked stale after response/evidence/metric changes
- deterministic fallback still works when LLM path fails
- metadata-only review is explicit when extraction failed or is still pending
- context trimming keeps the highest-ranked evidence chunks and reports omitted coverage

### Inline UX behavior
- compare view renders current vs suggested response
- apply-to-draft never mutates official saved response
- suggestion dismissal and usefulness feedback persist correctly
- frozen workspace blocks apply-to-draft but still allows explain/review

### Reviewer-mode behavior
- reviewer review flags unsupported claims
- reviewer review flags missing final evidence versions
- reviewer questions vary by body/version pack
- review severity changes with assistant config and metric alias rules

### Regression
- existing reporting/DVV/recommendation flows remain intact
- existing copilot gating by tenant feature still holds
- official scoring and official save semantics remain deterministic
- full accreditation suite remains green

## Assumptions and Defaults

- this phase builds on the already implemented reporting/copilot/body-config infrastructure
- provider/model routing remains platform-managed
- official saved responses remain side-effect free from AI generation
- extraction and grounding are advisory support layers, not new scoring inputs by default
- citations should favor precise chunk references over broad file-level references wherever possible
- extraction defaults to on-demand to keep OCR and storage cost proportional to actual copilot use

## Recommended Build Order

1. extraction pipeline hardening
   - PDF/text/image extraction
   - chunk model
   - extraction status and quality flags
2. citation and grounding builder
   - chunk selection
   - citation storage
   - stale detection
3. inline block copilot UX
   - compare
   - apply-to-draft
   - citation cards
4. reviewer-mode copilot
   - reviewer review
   - assessor question checklist
5. quality and safety hardening
   - anti-injection
   - privacy/redaction
   - large-context trimming
