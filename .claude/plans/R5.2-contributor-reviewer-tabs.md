## ⚠ Pre-Implementation Deviation: Fix `getKpiCrossComparison` Loose Coupling (from R5.1 Audit)

### Problem: Cross-Comparison Is Tightly Coupled to Numeric KPIs

`getKpiCrossComparison()` in `src/lib/kra-kpi/dashboard-service.ts` directly sums
`targetValue` and `actualValue` to compute per-unit comparison. This **only works for
NUMERIC, PERCENTAGE, and CURRENCY** measurement types. For the other 5 types (BOOLEAN,
RATING, MILESTONE, DATE_TARGET, GRADE), both fields are null, producing meaningless 0/0
results.

The rest of the dashboard layer is cleanly decoupled — it reads pre-computed scores
(`effectiveScore`, `computedScore`, `stageCompletionScore`) written by the scoring engine
in `scoring-service.ts`. The dashboard never imports scoring, reward, or measurement-type
logic. This one function is the only coupling leak.

### Fix (apply during R5.2 implementation)

Refactor `getKpiCrossComparison()` to use **pre-computed scores** instead of raw
target/actual values. This makes it measurement-type agnostic:

**Before** (current — numeric-only):
```typescript
entry.target += allocation.targetValue ?? 0;
entry.achieved += latestAchievement.actualValue ?? 0;
completionPercent = achieved / target * 100;
```

**After** (measurement-type agnostic):
```typescript
// Use the pre-computed 0-100 score from the scoring engine
const score = achievement?.effectiveScore
  ?? achievement?.stageCompletionScore
  ?? achievement?.computedScore
  ?? null;
entry.allocationCount += 1;
if (score != null) {
  entry.totalScore += score;
  entry.scoredCount += 1;
}
// Per-unit result: averageScore = totalScore / scoredCount
// completionPercent = scoredCount / allocationCount * 100
```

This change:
- Works identically for ALL 9 measurement types (NUMERIC, PERCENTAGE, CURRENCY, BOOLEAN, RATING, MILESTONE, DATE_TARGET, GRADE, and any future types)
- Uses the same `scoreFromAchievement()` pattern as `getOrgHierarchyStats` and `getPersonDetail`
- Keeps the dashboard fully isolated from the scoring engine — if scoring logic changes, dashboard still just reads stored scores
- Preserves the per-unit breakdown structure for the UI

**Return type update** — `KpiCrossComparison` type changes:
```typescript
// Before
units: { unitId, unitName, target, achieved, completionPercent, achievementCount }[]
// After
units: { unitId, unitName, allocationCount, averageScore, completionPercent, scoredCount }[]
```

And the top-level `targetTotal`/`achievedTotal` become `totalAllocations`/`overallAverageScore`.

**File changed**: `src/lib/kra-kpi/dashboard-service.ts` — `getKpiCrossComparison()` + `KpiCrossComparison` type.

**Impact**: The existing `admin-dashboard.tsx` does NOT call `getKpiCrossComparison` (confirmed in R5.1 audit — endpoint exists but is unused in current UI). The R5.3+ Organization tab will be the first consumer, so the type change is safe.

### Loose Coupling Audit Summary (from R5.1 review)

After this fix, the full dashboard stack is measurement-type agnostic:

| Dashboard Function | Reads | Coupling Status |
|-------------------|-------|-----------------|
| `getOverviewStats` | `state` counts, date comparisons | Fully isolated |
| `getOrgHierarchyStats` | `effectiveScore`/`computedScore` via `scoreFromAchievement()` | Fully isolated |
| `getKpiCrossComparison` | ~~`targetValue`/`actualValue`~~ → `effectiveScore`/`computedScore` | **Fixed** (was coupled) |
| `getAttentionItems` | `state` counts, `isCompleted`, `updatedAt` | Fully isolated |
| `getStageBottleneckAnalysis` | `isCompleted`, `completedAt`, `createdAt` | Fully isolated |
| `getPersonDetail` | `effectiveScore`/`computedScore` + `formatTargetValue()` for display | Fully isolated |

The system can now handle any KPI type change, new measurement types, new scoring
methods, or reward rule changes without touching the dashboard layer.


**Data flow**:
1. Fetch from `GET /api/tenant/kra-kpi/dashboard/review-queue?periodId=X`
2. Summary counts computed client-side from the queue data
3. FilterBar for unit (if user heads multiple), state, KPI
4. DataTable sorted by waiting days descending (stalest first — UX-9)
5. Row click expands inline detail (not slide-over — keeps context)

**Expanded row shows**:
- Achievement details: KPI title, target, actual, evidence links, score
- Text input for recommendation/rejection note
- Action buttons: Recommend (green), Send Back (amber), Reject (red)
- **⚠ Finding 5 fix**: Buttons call the EXISTING shared reviewer endpoint — do NOT reference nonexistent `/achievements/{id}/recommend` routes:
  - The actual API is: `POST /api/tenant/kra-kpi/my/recommend` with body `{ achievementId, approved: boolean, level: 'KEY'|'FINAL', remark? }`
  - The queue row's `reviewLevel` tells which `level` value to send
  - Recommend: `{ achievementId, approved: true, level: row.reviewLevel }`
  - Send Back: `{ achievementId, approved: false, level: row.reviewLevel, remark: "reason", rejectionType: "REVISE" }`
  - Reject: `{ achievementId, approved: false, level: row.reviewLevel, remark: "reason", rejectionType: "REJECT" }` (different UX — ConfirmDialog; backend stores `rejectionType` in `verificationLog` for audit trail)
  - If the KPI has both `keyUnitId` AND `finalUnitId`, a KEY-level recommend moves it to RECOMMENDED state for final verification; a FINAL-level approve moves it to VERIFIED
- After action: remove from queue, show success banner, update counts

**Stale indicator**:
- Waiting >7 days: amber warning icon + amber text
- Waiting >14 days: rose warning icon + rose text
