# R2.2 — Stages, Submission, Approval & Dashboard
# ═══════════════════════════════════════════════════════════════════════════════

## Goal

Build the employee-facing achievement workflow: weighted KPI stages with progress
tracking, template-driven submission with contribution roles, approval by
custodian unit, full submission trail, in-app notifications, and an admin
dashboard with org-hierarchy drill-down.

Everything builds on the R2.1 schema foundation. The `KpiStageDefinition` and
`KpiStageProgress` tables already exist. This release adds service logic, new
schema fields, API routes, and UI for the complete stage → submit → approve loop.

---

## Locked Decisions (from brainstorming)

| # | Decision |
|---|---|
| D1 | Stages are **progress milestones**, not approval gates. Employee updates them. |
| D2 | Each stage has a **weight**. Auto-score = sum of completed stage weights. No manual override. |
| D3 | Admin toggles **evidence required per stage** (checkbox). |
| D4 | Admin can set **optional deadline per stage**. |
| D5 | Multi-target KPIs use **tabs (≤5)** or **card list (>5)** — one per achievement instance. |
| D6 | `allowPartialCompletion` flag per KPI. If true → submit anytime. If false → all stages must be done. |
| D7 | **Contribution roles** with credit % defined on KPI (template library deferred to R2.3). |
| D8 | Approving authority = **source division** by default, overridable to another unit via `keyUnitId`/`finalUnitId`. |
| D9 | **Re-submission** allowed while period is IN_PROGRESS. |
| D10 | Full **submission trail** — every submit/reject/approve logged with timestamp, actor, notes. |
| D11 | **In-app notifications** — no email for now. |
| D12 | **No carry-forward**. One achievement claimed once. |
| D13 | Fixed weightages, no self-assessment, no subjective scoring. |
| D14 | KPIs without stages work exactly as R1 — submit button always available. |

## PART A: Schema Migration

### A1. Alter `KpiStageDefinition` — add weight, evidence, deadline fields

Current schema has: `id, kpiDefinitionId, stageOrder, title, description, isMandatory, createdAt, updatedAt`

**Add columns:**

```prisma
model KpiStageDefinition {
  // ... existing fields ...
  weight                Float          @default(0)     // contribution to total score
  evidenceRequired      Boolean        @default(false)
  evidenceTypes         EvidenceType[]                  // reuse existing enum
  evidenceInstructions  String?
  deadline              DateTime?                       // optional per-stage deadline
}
```

### A2. Alter `KpiStageProgress` — add achievement link, evidence files

Current schema links to `targetAllocationId`. For multi-target (multiple achievements
per allocation), we need to also link to `achievementId`.

**Add columns:**

```prisma
model KpiStageProgress {
  // ... existing fields ...
  achievementId     String?                            // nullable for backward compat
  notes             String?                            // user notes when marking done
  evidenceFiles     Json?                              // [{name, url, type, uploadedAt}]

  achievement       Achievement?  @relation(fields: [achievementId], references: [id], onDelete: Cascade)
}
```

**Add index:** `@@index([achievementId])`

Update unique constraint: change from `@@unique([targetAllocationId, stageDefinitionId])`
to `@@unique([targetAllocationId, stageDefinitionId, achievementId])` — so each
achievement instance under the same allocation gets its own stage progress set.

### A3. Alter `KpiDefinition` — add partial completion flag and contribution roles

```prisma
model KpiDefinition {
  // ... existing fields ...
  allowPartialCompletion  Boolean    @default(true)
  contributionRoles       Json?      // [{role, creditPercent, isDefault}]
}
```

`contributionRoles` example:
```json
[
  { "role": "First Author",         "creditPercent": 100, "isDefault": false },
  { "role": "Corresponding Author", "creditPercent": 80,  "isDefault": false },
  { "role": "Co-Author",            "creditPercent": 50,  "isDefault": true  },
  { "role": "Supervisor/Mentor",    "creditPercent": 30,  "isDefault": false }
]
```

### A4. Alter `Achievement` — add contribution role and stage score

```prisma
model Achievement {
  // ... existing fields ...
  title                 String?       // user-given name ("IoT Security Paper")
  contributionRole      String?       // "First Author", "Co-Author", etc.
  creditPercent         Float?        // 100, 80, 50, 30 — from role definition
  effectiveScore        Float?        // computedScore * (creditPercent / 100)
  stageCompletionScore  Float?        // sum of completed stage weights (before credit adjustment)
  stageProgress         KpiStageProgress[]  // relation back from KpiStageProgress
}
```

### A5. `Notification` model — already exists

The R2.1 migration already created the `Notification` model. No changes needed.

### A6. New model: `SubmissionTrail`

```prisma
model SubmissionTrail {
  id              String   @id @default(cuid())
  achievementId   String
  action          String   // SUBMITTED, APPROVED, REJECTED, RESUBMITTED, WITHDRAWN
  actorUserId     String
  actorName       String   // denormalized for trail readability
  actorRole       String   // "Employee", "HOD", "IQAC Admin"
  actorUnitName   String?  // department name
  note            String?
  scoreAtAction   Float?   // score at the time of this action
  metadata        Json?    // any extra context
  createdAt       DateTime @default(now())
  achievement     Achievement @relation(fields: [achievementId], references: [id], onDelete: Cascade)

  @@index([achievementId, createdAt])
}
```

Add relation on `Achievement`:
```prisma
  submissionTrail   SubmissionTrail[]
```

### A7. Migration summary

| Change | Type | Table |
|---|---|---|
| Add `weight`, `evidenceRequired`, `evidenceTypes`, `evidenceInstructions`, `deadline` | ALTER | KpiStageDefinition |
| Add `achievementId`, `notes`, `evidenceFiles` | ALTER | KpiStageProgress |
| Change unique constraint to include `achievementId` | ALTER | KpiStageProgress |
| Add `allowPartialCompletion`, `contributionRoles` | ALTER | KpiDefinition |
| Add `title`, `contributionRole`, `creditPercent`, `effectiveScore`, `stageCompletionScore` | ALTER | Achievement |

## PART B: Stage CRUD Service

**File**: `src/lib/kra-kpi/stage-service.ts` (NEW)

### B1. `createStage(kpiId, tenantId, data, actorUserId, actorRole)`

- Permission: admin/owner only
- Validate KPI exists, belongs to tenant, not ARCHIVED
- Validate `stageOrder` is unique for this KPI (or auto-assign next order)
- Validate `weight >= 0`
- Validate evidence types are valid enum values if evidenceRequired = true
- Validate deadline is within the KPI's assessment period date range (if set)
- Create `KpiStageDefinition` record
- Audit log

**Input schema:**
```typescript
{
  title: string;           // required, max 200 chars
  description?: string;    // max 500 chars
  stageOrder?: number;     // auto-assign if omitted
  weight: number;          // >= 0
  isMandatory?: boolean;   // default true
  evidenceRequired?: boolean; // default false
  evidenceTypes?: EvidenceType[];
  evidenceInstructions?: string;
  deadline?: Date;
}
```

### B2. `updateStage(stageId, kpiId, tenantId, data, actorUserId, actorRole)`

- Same permission + validation as create
- Cannot change `stageOrder` directly — use `reorderStages` for that
- Can update: title, description, weight, isMandatory, evidence settings, deadline
- **Locking rule**: if any achievement has stage progress for this stage with
  `isCompleted = true`, warn but allow update (admin responsibility)
- Audit log

### B3. `deleteStage(stageId, kpiId, tenantId, actorUserId, actorRole)`

- Permission: admin/owner
- **Locking rule**: if any KpiStageProgress exists for this stage with
  `isCompleted = true`, reject with error "Stage has completed progress records.
  Delete progress first or archive the stage."
- If no completed progress: cascade delete (KpiStageProgress records auto-deleted)
- Re-order remaining stages to close gaps
- Audit log

### B4. `listStages(kpiId, tenantId)`

- Returns `KpiStageView[]` ordered by `stageOrder`
- Includes aggregate: count of completed progress records per stage (across all allocations)
- No permission restriction — visible to anyone in the tenant

### B5. `reorderStages(kpiId, tenantId, orderedIds[], actorUserId, actorRole)`

- Takes array of stage IDs in desired order
- Updates `stageOrder` for each (1, 2, 3, ...)
- Validate all IDs belong to this KPI
- Audit log

### B6. `getStageWeightSummary(kpiId, tenantId)`

- Returns: `{ totalWeight, stages: [{title, weight, percentage}] }`
- Used by admin UI to show weight distribution
- Example: total = 100, stages = [{Topic: 10, 10%}, {Writing: 25, 25%}, ...]

## PART C: Stage Progress Service

**File**: `src/lib/kra-kpi/stage-progress-service.ts` (NEW)

### C1. `initializeStageProgress(achievementId, targetAllocationId, kpiId)`

- Called when employee creates a new achievement instance
- Fetches all `KpiStageDefinition` records for the KPI
- Creates one `KpiStageProgress` record per stage, all `isCompleted = false`
- Links to both `targetAllocationId` and `achievementId`

### C2. `markStageComplete(progressId, tenantId, data, actorUserId)`

- Validate the progress record exists
- Validate the actor is the allocated employee (or unit head with override)
- Validate period is IN_PROGRESS
- If stage has `evidenceRequired = true`:
  - Validate `evidenceFiles` is provided and non-empty
  - Validate file types match `evidenceTypes` on the stage definition
- Set `isCompleted = true`, `completedAt = now()`, `completedByUserId = actorUserId`
- Store `notes` and `evidenceFiles`
- Recalculate `stageCompletionScore` on the Achievement = sum of completed stage weights
- Check if all stages complete → update achievement readiness flag
- Create notification if stage has deadline and was completed late
- Audit log

**Input:**
```typescript
{
  notes?: string;
  evidenceFiles?: Array<{ name: string; url: string; type: string }>;
}
```

### C3. `unmarkStageComplete(progressId, tenantId, actorUserId)`

- Allow employee to undo a stage completion (mistakes happen)
- Only if achievement is still in DRAFT state (not yet submitted)
- Reset `isCompleted = false`, clear `completedAt`, `completedByUserId`
- Recalculate `stageCompletionScore`
- Audit log

### C4. `getStageProgressForAchievement(achievementId, tenantId)`

- Returns `StageProgressView[]` ordered by stage order
- Includes stage definition details (title, weight, evidenceRequired, deadline)
- Includes completion status, timestamp, notes, evidence files
- Includes computed fields:
  - `isOverdue`: deadline < now && !isCompleted
  - `daysRemaining`: deadline - now (null if no deadline)

### C5. `getStageProgressSummary(targetAllocationId, tenantId)`

- For admin/dashboard view
- Groups by achievement instance under this allocation
- Returns per-achievement: `{ achievementId, title, completedStages, totalStages, completionPercent, stageScore, totalWeight }`

### C6. `calculateStageScore(achievementId)`

- Pure calculation: sum of `weight` for all stages where `isCompleted = true`
- Updates `Achievement.stageCompletionScore`
- If contribution role set: `effectiveScore = stageCompletionScore * (creditPercent / 100)`
- Returns `{ stageCompletionScore, effectiveScore }`

## PART D: Submission Flow Service

**File**: `src/lib/kra-kpi/achievement-service.ts` (MODIFY existing)

### D1. Modify `createAchievement` — support named instances + contribution role

Current flow: employee creates achievement linked to allocation.

**New behavior:**
- Accept optional `title` field (user names the achievement, e.g. "IoT Security Paper")
- Accept optional `contributionRole` from the KPI's `contributionRoles` list
- If role selected → look up `creditPercent` from KPI definition and store on achievement
- After creating achievement → call `initializeStageProgress()` to set up stage checklist
- If KPI has no stages defined → skip stage initialization (R1 behavior preserved)

### D2. Modify `submitAchievement` — enforce stages + evidence

Current flow: DRAFT → SUBMITTED.

**New validation before submission:**

```
1. If KPI has stages defined:
   a. If allowPartialCompletion = false:
      → ALL stages must be isCompleted = true
      → Error: "Complete all stages before submitting"
   b. If allowPartialCompletion = true:
      → At least 1 stage must be complete (can't submit with 0 progress)
      → Warning only, allow submit

2. If KPI.evidenceRequired = true (KPI-level evidence, separate from stage evidence):
   → Achievement must have evidenceFiles or evidenceLinks
   → Error: "Evidence is required for this KPI"

3. Per-stage evidence:
   → Each completed stage with evidenceRequired = true must have evidenceFiles
   → Already enforced at markStageComplete time, not re-checked here

4. Contribution role:
   → If KPI has contributionRoles defined and achievement.contributionRole is null:
      → Error: "Please select your contribution role"

5. Period must be IN_PROGRESS
   → Error: "Submissions are closed for this period"
```

**After validation passes:**
- Set `state = SUBMITTED`
- Calculate `stageCompletionScore` = sum of completed stage weights
- Calculate `effectiveScore` = stageCompletionScore * (creditPercent / 100)
- Determine approving unit:
  - If `KpiDefinition.finalUnitId` is set → use it (override)
  - Else if `KpiDefinition.keyUnitId` is set → use it
  - Else → use `KpiDefinition.startingUnitId` (source division default)
- Set `currentVerifierUnitId` on achievement
- Find unit head(s) of approving unit → set `currentVerifierUserId`
- Create `SubmissionTrail` record: action = "SUBMITTED"
- Create `Notification` for approver: "Dr. Sharma submitted achievement for Research Publications"
- Audit log

### D3. Modify `recommendAchievement` → rename/repurpose as `approveAchievement`

In R2.2, the 2-level flow (RECOMMEND → VERIFY) simplifies for most cases to:
- Source division approves → VERIFIED

**But** keep backward compatibility: if both `keyUnitId` and `finalUnitId` are set:
- Key unit recommends (SUBMITTED → RECOMMENDED)
- Final unit verifies (RECOMMENDED → VERIFIED)

If only source division:
- Source division approves (SUBMITTED → VERIFIED directly)

### D4. `resubmitAchievement(achievementId, tenantId, actorUserId)`

- Only allowed when `state = REJECTED`
- Only allowed when period is IN_PROGRESS
- Reset `state = DRAFT` (employee can update stages/evidence before resubmitting)
- Create `SubmissionTrail` record: action = "RESUBMITTED"
- Clear `rejectionReason`
- Notification to employee: "You can now update and resubmit"

### D5. Modify `rejectAchievement` — add trail

- Existing rejection logic stays
- **Add**: Create `SubmissionTrail` record: action = "REJECTED", include reason
- **Add**: Notification to employee: "Your achievement was rejected. Reason: ..."

### D6. Score calculation flow

```
Achievement score calculation:

If KPI has stages:
  stageCompletionScore = sum(completed stage weights)

  If contributionRole set:
    effectiveScore = stageCompletionScore × (creditPercent / 100)
  Else:
    effectiveScore = stageCompletionScore

If KPI has NO stages:
  Use existing R1 computeScore() based on actual vs target values

  If contributionRole set:
    effectiveScore = computedScore × (creditPercent / 100)
  Else:
    effectiveScore = computedScore

The effectiveScore is what appears on the employee's scorecard.
```

## Assumptions

1. File upload infrastructure (S3, local storage) does NOT exist yet. Evidence files
   in R2.2 are **URL references only** (user pastes a link or provides a URL to an
   externally hosted file). Actual file upload with binary storage is deferred to R2.3.

2. The Notification model already exists in the schema (added in R2.1 migration cycle).
   No migration needed for it.

3. Existing 2-level verification (RECOMMEND → VERIFY) is preserved. R2.2 adds
   submission trail and stage-aware scoring on top of it, not replacing it.

4. Stage weights are absolute values (not percentages). The admin is responsible for
   making them sum to a meaningful total. The system shows the total but does not
   enforce it equals the KPI weightage.

5. Contribution role credit percentages reduce the effective score but do NOT change
   the target value. A co-author with 50% credit on a target of 3 papers still needs
   to submit 3 achievement instances, but each counts as 0.5 toward their scorecard.

6. Dashboard queries use direct Prisma aggregations. No materialized views or
   background jobs in this release. If performance is an issue with large datasets,
   caching/materialization moves to R2.3.
