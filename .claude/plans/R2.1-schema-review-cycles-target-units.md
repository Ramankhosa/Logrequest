# ═══════════════════════════════════════════════════════════════════════════════
# Prerequisites: R1 + R1.1a + R1.2a fully merged to master
# Estimated effort: Opus 4.6 recommended

## Goal

Lay the complete R2 schema foundation in ONE migration (all new enums, models, and
columns for R2.1–R2.4), then build the two simplest features on top:
1. **Stored Review Cycles** — persisted sub-period tracking with current-cycle detection
2. **Multi-Target Units** — assign multiple departments as target recipients for a KPI

Everything in this plan is non-breaking — nullable columns and new tables only.
Existing R1/R1.1a data is untouched.

### B2: Extend period-service.ts — generateReviewCycles()

**File**: `src/lib/kra-kpi/period-service.ts`

Add the following function. It uses the existing `computeReviewCycles()` pure function

```ts
/**
 * Generate and persist ReviewCycle records for a period.
 *
 * Behavior:
 * - Deletes any existing ReviewCycle rows for this period (idempotent)
 * - Computes cycles from period dates + frequency using existing computeReviewCycles()
 * - Creates ReviewCycle rows with correct isCurrent flag
 * - Returns the created cycles
 *
 * When to call:
 * - Automatically when period transitions to IN_PROGRESS
 * - Manually via API to regenerate (e.g., after changing dates or frequency)
 *
 * Edge cases:
 * - Period with ANNUAL frequency and 1-year range → 1 cycle
 * - Period with DAILY frequency and 1-year range → 365/366 cycles (capped at 366)
 * - Period dates changed after cycles generated → call regenerate
 * - Frequency changed → call regenerate
 */
export async function generateReviewCycles(
  periodId: string,
  tenantId: string,
  actorUserId: string,
  actorRole: Role
): Promise<KraKpiActionResult & { data?: StoredReviewCycleView[] }> {
  if (!isAdminOrOwner(actorRole)) {
    return { status: "error", message: "Insufficient permissions." };
  }

  const period = await prisma.assessmentPeriod.findFirst({
    where: { id: periodId, tenantId },
  });
  if (!period) {
    return { status: "error", message: "Assessment period not found." };
  }

  // Compute cycles using existing pure function
  const computed = computeReviewCycles(
    period.startDate,
    period.endDate,
    period.reviewFrequency
  );

  if (computed.length === 0) {
    return { status: "error", message: "No review cycles could be generated for this period's date range and frequency." };
  }

  // Transaction: delete old cycles + create new ones
  const created = await prisma.$transaction(async (tx) => {
    // Delete existing cycles for this period (idempotent regeneration)
    await tx.reviewCycle.deleteMany({ where: { periodId } });

    // Create new cycles
    const cycles = [];
    for (const c of computed) {
      const cycle = await tx.reviewCycle.create({
        data: {
          periodId,
          cycleNumber: c.cycleNumber,
          label: c.label,
          startDate: c.startDate,
          endDate: c.endDate,
          isCurrent: c.isCurrent,
          // reviewDeadline: could be computed as endDate + gracePeriodDays
        },
      });
      cycles.push(cycle);
    }

    await tx.auditLog.create({
      data: {
        tenantId,
        actorUserId,
        actorRole,
        targetType: "ReviewCycle",
        targetId: periodId,
        action: "GENERATE",
        metadata: { cycleCount: cycles.length, frequency: period.reviewFrequency },
      },
    });

    return cycles;
  });

  return {
    status: "success",
    message: `${created.length} review cycle(s) generated.`,
    data: created.map((c) => ({
      id: c.id,
      periodId: c.periodId,
      cycleNumber: c.cycleNumber,
      label: c.label,
      startDate: c.startDate,
      endDate: c.endDate,
      reviewDeadline: c.reviewDeadline,
      isCurrent: c.isCurrent,
      createdAt: c.createdAt,
    })),
  };
}
```

### B4: Add updateCurrentCycle()

```ts
/**
 * Refresh the isCurrent flag on all cycles for a period based on today's date.
 * Call this periodically (e.g., via cron or on page load) or when the period
 * date range changes.
 */
export async function updateCurrentCycle(
  periodId: string,
  tenantId: string
): Promise<KraKpiActionResult> {
  const period = await prisma.assessmentPeriod.findFirst({
    where: { id: periodId, tenantId },
    select: { id: true },
  });
  if (!period) {
    return { status: "error", message: "Period not found." };
  }

  const now = new Date();
  const cycles = await prisma.reviewCycle.findMany({
    where: { periodId },
    orderBy: { cycleNumber: "asc" },
  });

  await prisma.$transaction(async (tx) => {
    for (const cycle of cycles) {
      const shouldBeCurrent = now >= cycle.startDate && now < cycle.endDate;
      if (cycle.isCurrent !== shouldBeCurrent) {
        await tx.reviewCycle.update({
          where: { id: cycle.id },
          data: { isCurrent: shouldBeCurrent },
        });
      }
    }
  });

  return { status: "success", message: "Current cycle updated." };
}
```

## Edge Cases & Pitfalls

1. **Schema conflict**: The new OrgUnit relations (`kpiKeyUnit`, `kpiFinalUnit`, `kpiTargetUnits`)
   must use DIFFERENT relation names than the existing `kpiStarting` relation. Prisma requires
   unique relation names when a model has multiple FK columns pointing to the same table.

2. **Review cycle date overlap**: When the period end date doesn't align perfectly with
   the frequency boundary (e.g., quarterly in a 10-month period), the last cycle is
   shorter. The existing `computeReviewCycles()` already handles this by capping at endDate.

3. **Target share rounding**: When computing target values from shares (e.g., 33.33% of 100),
   use `Math.round()` and verify the sum matches. If rounding causes a 1-unit discrepancy,
   add the remainder to the first/last unit.

4. **KpiDefinition view types**: After adding new fields to `KpiDefinitionView`, ALL code
   that constructs this type must be updated. Search for `KpiDefinitionView` across the
   codebase and update every mapper. The key files:
   - `src/lib/kra-kpi/kpi-service.ts` (listKpis, getKpi)
   - Any component that destructures KpiDefinitionView

5. **OrgUnit relation naming**: Prisma requires explicit relation names when a model has
   multiple foreign keys to the same target. The current schema already uses
   `@relation("KpiStartingUnit")`. The new ones must be:
   - `@relation("KpiKeyUnit")`
   - `@relation("KpiFinalUnit")`
   - `@relation("KpiTargetUnits")`

6. **flowStatus default**: When the migration runs, all existing TargetAllocations get
   `flowStatus = CREATED`. This is correct — they were created under R1 which didn't
   have the flow concept. R2.4 will handle transitioning existing allocations.

7. **EvidenceType is an ARRAY**: `evidenceTypes EvidenceType[]` is a Postgres array column.
   Prisma handles this natively in PostgreSQL but it behaves differently from a single enum.
   Make sure the Zod schema validates as an array.
