# R3.4A/B: Workspace Reporting, Post-Filing Ops, and Accreditation Copilot

## Summary

Build the next accreditation module as a workspace-first reporting and assistance layer with two tightly connected parts:

1. Deterministic reporting and post-filing operations
   - readiness, completeness, evidence inventory, export
   - DVV query tracking
   - peer-team recommendation tracking
2. Grounded accreditation copilot
   - block-level and workspace-level assistance
   - per-body assistants from day one
   - sidecar suggestions only, never direct writes to official responses
   - hybrid evidence grounding: metadata first, extracted evidence text only for explicitly processed files

Chosen defaults:
- start with reporting plus copilot, not competitive benchmarking first
- UI is embedded into the existing workspace surfaces
- exports are JSON and CSV only
- access is mixed: reports are readable by collaborators, but management actions stay admin/coordinator-only
- read-only reporting appears in both `WorkspaceManager` and `WorkspaceCollaborationHub`
- AI is a full copilot, but official scores and final saved responses remain deterministic and manual
- adaptation is per-body assistants, not one generic assistant
- AI writes only to assistant sidecar suggestions, never directly to `BlockEntryResponse`

Out of scope for this phase:
- competitor institutions, peer groups, rankings, benchmark dashboards
- full cross-accreditation reconciliation or automatic consistency enforcement
- PDF or SSR-style narrative export

## Why This Is Next

The accreditation foundation is already in place:
- block-native scoring is implemented
- institutional data bank is implemented
- workspace projection is implemented
- migration history is repaired for fresh deploys

The next high-value gap is the operational output layer that teams actually use while preparing and defending a filing:
- Are we ready?
- What is missing?
- What evidence is weak?
- What should we export?
- What questions is the assessor likely to ask?
- How do we track DVV and peer recommendations after submission?

## User Assistance Goals

The app should help users answer practical accreditation questions:
- What does this block really require?
- What data or narrative is still missing?
- What evidence should be attached?
- Is the response weak, inconsistent, unsupported, or risky?
- Draft a stronger response from what is already filled.
- What likely reviewer or assessor questions should we prepare for?
- Which blocks need attention first before review or freeze?

AI at this layer is advisory only:
- it explains
- it reviews
- it drafts suggestions
- it prioritizes risk
- it never becomes the source of record

## Key Changes

### 1. Deterministic reporting and post-filing models

Add workspace-linked models:
- `DvvQuery`
- `PeerRecommendation`

Add AI-related models:
- `EvidenceVersionExtraction`
  - one row per processed evidence version
  - stores extraction status, content hash, extracted text or structured chunks, and processing metadata
  - used only when a file is explicitly processed for AI grounding
- `AccreditationAssistantSuggestion`
  - scope: `WORKSPACE` or `BLOCK_ENTRY`
  - type: `GUIDANCE`, `REVIEW`, `DRAFT`, `RISK`, `QUESTION_CHECKLIST`
  - stores generated content, structured payload, citations, source hash, grounding status, confidence, actor, and timestamps

Do not add competitor, peer-group, or public benchmark models in this phase.

### 2. Data model requirements

The new models must be specific enough that implementors do not invent incompatible status sets or payload shapes.

`DvvQuery` must include:
- workspace link
- `linkedBlockIds: string[]` so one query can target multiple blocks
- body reference number, query text, status, priority, received date, due date
- assignment to either `assignedToUserId` or external assignee fields
- response text, response attachment metadata, responded-at metadata
- creator and audit timestamps

`PeerRecommendation` must include:
- workspace link
- `linkedBlockIds: string[]`
- recommendation text, priority, status
- action plan, target date, completed-at state
- assignment to either `assignedToUserId` or external assignee fields
- progress notes with timestamped updates
- creator and audit timestamps

`AccreditationAssistantSuggestion` must include:
- workspace link and optional `entryId`
- scope and type enums
- `assistantPackKey`
- human-readable content plus optional structured payload
- citations array, grounding status, confidence
- `sourceHash` for staleness detection
- status lifecycle with at least `ACTIVE`, `ACCEPTED`, `DISMISSED`, and `STALE`
- accepted and dismissed actor metadata

`EvidenceVersionExtraction` must include:
- unique link to evidence version
- extraction status lifecycle
- extracted text and structured chunks
- content hash for invalidation
- processing metadata, file type, page count, processed-at timestamp

### 3. Reporting service layer

Create a new reporting service that composes existing workspace logic instead of duplicating scoring or workflow rules.

Core deterministic functions:
- `getWorkspaceReadinessReport(...)`
- `getWorkspaceCompletenessReport(...)`
- `getWorkspaceEvidenceInventory(...)`
- `exportWorkspaceReport(..., format)`
- DVV CRUD and summary functions
- recommendation CRUD and summary functions
- `getCrossWorkspaceOverlapReport(tenantId)` for advisory-only overlap warnings

Behavior:
- readiness report wraps existing readiness and enriches it with score state, freeze eligibility, blocker and warning counts, progress percentages, and stale-score flags
- completeness report is block-wise and year-aware
- evidence inventory checks linked evidence, final-version presence, and required-evidence gaps
- export returns structured JSON or flattened CSV
- overlap report flags shared metrics across active workspaces, stale/fresh mismatches, and likely cross-filing contradictions

Implementation rule:
- reuse existing workspace scoring, readiness, manifest, evidence, and drift helpers wherever possible

### 4. Copilot architecture

Create an accreditation AI service with per-body assistant registries:
- `NAACAssistant`
- `NBAAssistant`
- `NIRFAssistant`
- fallback behavior for unsupported body or version

Each assistant shares a common runtime contract but owns:
- criterion interpretation style
- evidence expectations
- narrative structure
- review heuristics
- likely assessor or reviewer questions
- prohibited-claim rules

Add body and block assistant configuration:
- `AccreditationBodyVersion.assistantPackKey`
- `CriterionBlock.assistantConfig Json?`

AI capabilities:
- `Explain`: what the block means, what the user should provide, what evidence is expected
- `Review`: critique the currently filled response against scoring, evidence, and data rules
- `Draft`: generate a suggested narrative or structured response draft as a sidecar artifact
- `Watchlist`: workspace-level risk, gap, overlap, and next-action summary

Non-negotiable rules:
- AI never mutates `BlockEntryResponse` directly
- AI never changes scores
- AI must cite its grounding
- if grounding is insufficient, it must say so explicitly
- no unsupported public or world-knowledge claims inside official response suggestions

### 5. Assistant configuration and prompt contracts

`CriterionBlock.assistantConfig` must follow a defined contract rather than free-form JSON.

Quantitative or computed blocks need config for:
- review focus on data accuracy
- formula parity checks
- slab-boundary warnings
- linked data-bank source suggestions
- manual-override divergence warnings

Qualitative or narrative blocks need config for:
- required narrative elements
- banned phrases or unsupported claim patterns
- tone guide
- min and max word guidance
- maximum unsupported claims before warning

The assistant runtime should treat this as a discriminated schema, not an untyped blob.

Every copilot action must use a stable prompt context object including:
- body and version identity
- assistant pack key
- block metadata
- current response state
- evidence metadata
- extracted evidence when available
- linked data-bank metrics
- workspace summary for watchlist

Prompt behavior by action:
- `Explain` stays instruction-focused and never invents facts
- `Review` checks data completeness, evidence sufficiency, unsupported claims, and risk near scoring boundaries
- `Draft` uses only grounded context and explicitly marks missing information
- `Watchlist` ranks the top risks and next actions by severity and readiness impact

### 6. Grounding model

Ground AI on:
- block metadata: title, type, scoring rule, validation rules, expected evidence, assistant config
- current block response data
- linked evidence metadata
- workspace readiness, gap, and drift state
- institutional data bank metrics projected or linked to the block
- extracted evidence text only when an evidence version has a successful extraction record

Hybrid evidence policy:
- v1 review works without extraction
- if extraction exists, AI may quote or summarize extracted snippets with citation references
- unprocessed files remain metadata-only

### 7. Suggestion lifecycle, staleness, and cost controls

Suggestion staleness rules:
- on block response save, recompute `sourceHash`; if it differs from ACTIVE suggestions for that entry, mark them `STALE`
- on evidence link or version change for a linked entry, mark ACTIVE suggestions `STALE`
- on evidence extraction reprocessing with a new content hash, mark citing suggestions `STALE`
- stale suggestions are never auto-regenerated; the user must explicitly rerun the action

Caching and rate limiting:
- cache by `(entryId or workspaceId, type, sourceHash)` and return the existing ACTIVE suggestion if unchanged
- enforce per-workspace and per-tenant usage caps
- throttle workspace watchlist regeneration
- set token budgets per action type
- log token count, duration, cached-hit status, tenant, workspace, and action type for monitoring

### 8. Access model

Reports:
- readable by any user who can already read the workspace

DVV and recommendation mutations:
- coordinator or admin only

AI usage:
- workspace-level watchlist readable by any workspace reader
- block-level explain, review, and draft available to users who can read the block
- accepting a suggestion into the editor is allowed for users who can edit that block
- accept means copy into client-side draft or editor state or mark acknowledged, not auto-save official response
- frozen workspaces allow AI review and explain, but not AI-assisted write-to-draft actions

### 9. UI shape

Do not create a standalone reporting page in this phase.

`WorkspaceManager`:
- add tabs or sections for `Reports`, `DVV`, `Recommendations`, and `Copilot`
- include block-level assistant actions from the entry list or detail panel
- include export buttons

`WorkspaceCollaborationHub`:
- add read-only reporting panels
- add collaborator-facing block assistant actions
- do not expose admin-only DVV or recommendation mutations here

Copilot UX:
- block side panel with `Explain`, `Review`, and `Draft`
- workspace watchlist panel with prioritized risks, likely reviewer questions, overlap warnings, and next actions
- suggestion cards with citations and accept or dismiss controls

- linked accreditation targets use `blockIds: string[]`
- AI responses always include `citations[]`, `confidence`, and `groundingStatus`
- export route validates `format`
- JSON export uses a stable top-level structure containing workspace metadata, block rows, evidence summary, DVV items, recommendations, and summary counters
- CSV export flattens block-level data into a deterministic row format, typically one row per block-year or equivalent response unit
- assistant suggestion acceptance never directly persists official block response data

## Edge Cases and Intelligent Behavior

The module must explicitly handle:
- different accreditation bodies interpreting the same institutional metric differently
- institution-level versus program-level accreditations
- quantitative-only blocks, qualitative-only blocks, and hidden calculation blocks
- manual-only or non-scoring blocks
- missing years versus zero values versus not-applicable cases
- stale institutional data being referenced in narratives
- response text claiming things not supported by evidence or metrics
- evidence attached but no final version marked
- scanned or unextractable files
- extremely large evidence sets that exceed model context
- frozen workspaces where advice is allowed but editing assistance is restricted
- unsupported body, version, or block assistant pack
- assistant outputs that lack grounding
- stale AI suggestions after response or evidence changes
- different block types needing different assistant review strategies
- multiple active filings using the same data but requiring different framing
- shared data-bank metrics producing cross-workspace inconsistencies
- excessive AI usage and repeated no-change reruns

Intelligent app behaviors should include:
- explaining what a criterion wants in body-specific language
- identifying missing data, missing evidence, or missing narrative support
- warning when a response over-claims beyond attached evidence or data bank metrics
- drafting stronger responses using only grounded workspace context
- generating likely assessor or reviewer question checklists
- surfacing a prioritized workspace watchlist of risky or incomplete blocks
- surfacing advisory overlap warnings across active filings that share institutional metrics

## Test Plan

### Reporting and post-filing
- readiness report matches existing blocker and warning logic
- completeness report marks missing years, no-response blocks, and evidence gaps correctly
- evidence inventory groups evidence by block and flags missing required evidence and missing final versions
- JSON and CSV exports are valid and stable
- overlap report flags shared metric inconsistencies across active workspaces without mutating data
- DVV CRUD, respond, and summary flows work
- recommendation CRUD, progress, and summary flows work
- collaborator read access and coordinator-only mutation rules are enforced

### Copilot grounding
- explain action uses block, version, body config, and current response state
- review action flags unsupported claims when evidence or data is missing
- draft action produces sidecar suggestion only
- assistant citations resolve to block response fields, evidence refs, or extraction snippets
- unsupported body or version returns graceful unavailable state
- frozen workspace blocks write-assist acceptance but still allows explain and review

### Assistant config and prompt behavior
- quantitative block configs drive formula, boundary, and override review behavior
- qualitative block configs drive narrative quality and banned-phrase review behavior
- prompt assembly always includes the required stable context fields for the selected action

### Suggestion lifecycle and cost controls
- response save marks prior ACTIVE suggestions stale when the grounding hash changes
- evidence link, evidence version, and extraction changes mark dependent suggestions stale
- repeated AI calls with unchanged source hash return cached suggestions
- workspace and tenant AI caps are enforced without breaking deterministic reporting features

### Extraction
- extraction record created for supported file processing
- unextractable or failed files fall back to metadata-only review
- extraction hash changes invalidate older suggestion grounding

### Cross-body adaptability
- the same metric under different body packs produces different guidance and review framing
- program-level accreditation blocks do not accidentally use institution-wide heuristics
- narrative-heavy and numeric-heavy blocks both receive appropriate assistant behavior

### Regression
- existing workspace readiness, data-gap, manifest, and drift flows remain unchanged
- full accreditation suite stays green

## Assumptions and Defaults

- This is the next module after reporting, data-bank, and scoring foundation, not full public benchmarking.
- Competitive benchmarking and full cross-accreditation reconciliation are deferred to later phases.
- Advisory cross-workspace overlap detection is included in this phase, but it remains read-only and non-blocking.
- There is no existing evidence-text pipeline, so extraction is introduced only for selected processed files.
- AI provider choice remains implementation-level, but the module must use a provider-agnostic service boundary.
- Official scoring remains deterministic; AI is advisory only.
- Per-body assistants are required from the start, even if only the initial supported bodies are configured in v1.
- This file is a scoped next-phase plan and does not replace the broader `.claude/plans/R3.4-competitive-analysis-reporting.md` roadmap.
