# R1.2a — Engagement & Discovery

## Context

R1.1a delivered the core assignee experience: My KPIs page with My Targets, Review Queue, and My Dashboard tabs. Faculty can see allocated KPIs, record achievements with dynamic template forms (PUBLICATION, PATENT, etc.), submit for 2-level verification (recommend → verify), cascade targets, withdraw submissions, and filter/sort allocations.

R1.2a adds the **engagement layer**: notifications to keep users informed, additional achievements for unallocated KPIs, workspace dashboard integration, bulk operations, and category quick-access.

### What R1.1a Built (Dependencies for R1.2a)

- Schema: `RECOMMENDED` state, `achievementFormConfig`/`achievementFormData`, `recommendedByUserId`/`recommendedAt`/`recommendationNote`, `verificationLog`, `Notification` model
- Services: `my-kpi-service.ts`, `assignee-access.ts`, updated `achievement-service.ts` with 2-level flow
- UI: `/my-kpis` page with `my-kpi-hub.tsx`, allocation cards, dynamic forms, review items, cascade forms, dashboard
- API: 9 routes under `/api/tenant/kra-kpi/my/`
- State management: KRA activates → all child KPIs activate. KPI individual state toggle (DRAFT ↔ ACTIVE) with parent KRA state guard. `getMeasurementCapValue()` enforces max allocation caps per measurement config.

### Key Architecture Notes

- Capping: `measurementConfig.maxValue` (NUMERIC/PERCENTAGE/CURRENCY) or `measurementConfig.maxRating` (RATING) serves as the allocation cap. Enforced in `target-service.ts` at allocation + cascade time. No separate `maxAllocationValue` field — it's embedded in the measurement config.
- State linkage: `changeKraState()` cascades state to all non-archived child KPIs in a transaction. `changeKpiState()` requires parent KRA to be ACTIVE before individual KPI can activate.
- 2-level verification: SUBMITTED → dept head RECOMMENDS → source dept head VERIFIES. Shortcut: if assignee's unit === KPI's `startingUnitId`, skip RECOMMENDED step.

# Edge Cases & Validation Rules
# ═══════════════════════════════════════════════════════════════════════════════

### Notifications
1. **User deleted** — Cascade delete notifications (already handled by Prisma `onDelete: Cascade`)
2. **Notification flood** — For period state change with 200 users, use `createBulkNotifications()` with `createMany()` not individual creates
3. **Duplicate notifications** — Don't create duplicate if same event fires twice (idempotency via entityType + entityId + type + userId unique check, or just allow — notifications are informational)
4. **Self-notification** — Don't notify the actor (e.g., if admin allocates to themselves, skip notification)
5. **No unit head** — If `resolveUnitHead()` returns null (unit has no head), skip notification silently (log warning)

### Additional Achievements
6. **Already allocated** — User has TargetAllocation for KPI → "Already allocated" message, redirect to My Targets
7. **Multiple additional for same KPI** — Block if user already has an existing additional achievement (any state except VERIFIED for current cycle). After VERIFIED, allow for next cycle.
8. **KPI not ACTIVE** — Don't show in available KPIs list
9. **Period not IN_PROGRESS/UNDER_REVIEW** — Block recording, show message
10. **No defaultTarget** — Score = null, show "Score will be assessed by verifier"
11. **Verification flow** — Same 2-level: who recommends? The user's dept head. Who verifies? The KPI's `startingUnit` head. Same shortcut logic applies.
12. **Which unit for recommendation?** — Use user's primary unit (first `memberOfUnits` entry). If user is in multiple units, use the first one.

### Bulk Submit
13. **Mixed states** — Only submit DRAFT achievements, skip others silently
14. **Validation failure** — If one achievement fails validation (e.g., missing required form field), report it in response but continue with others
15. **Empty list** — Return early with `{ submitted: 0, failed: [] }`

### Dashboard Bubble
16. **No allocations** — Hide card entirely (don't show empty card)
17. **Multiple periods** — Show summary for the most recent IN_PROGRESS or UNDER_REVIEW period. If none, show most recent CLOSED period.
18. **User is admin only** — Admin with no personal allocations → hide card

## E2E-1: Full Notification Lifecycle

```
1. Admin allocates Publications KPI to CS Dept (target: 50)
   → CS HOD receives notification (bell badge: 1)
2. HOD clicks notification → navigates to My KPIs → sees Publications
3. HOD cascades to 3 faculty (10, 20, 20)
   → Each faculty receives notification (bell badge: 1 each)
4. Dr. Kumar clicks notification → sees Publications (target: 10)
5. Dr. Kumar records achievement (actual: 12) → submits
   → HOD receives notification (bell badge: 1)
6. HOD clicks → Review Queue → recommends with note
   → Dean receives notification
7. Dean clicks → Review Queue → verifies
   → Dr. Kumar receives notification: "Verified! Score: 100"
8. Dr. Kumar sees badge, clicks → reads notification → badge clears
```

```
1. Dr. Kumar has Publications allocated (target: 10)

7. Goes through verification (recommend → verify)

```
