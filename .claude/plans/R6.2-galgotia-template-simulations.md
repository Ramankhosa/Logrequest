### Scenario 1.2: First author GU + 2 GU co-authors, Q2 journal (Galgotia Case 2/5)

**Input**:
```
achievementFormData: { journalQuartile: "Q2", doi: "10.5678/def" }
contributors: [
  { userId: "u1", creditPercent: 60, selectorTags: ["FIRST_AUTHOR"], isExcludedFromReward: false },
  { userId: "u2", creditPercent: 20, selectorTags: ["CO_AUTHOR"], isExcludedFromReward: false },
  { userId: "u3", creditPercent: 20, selectorTags: ["CO_AUTHOR"], isExcludedFromReward: false },
]
```

**Trace**:

1. `getEligibleContributors` → 3 eligible
2. `buildTierMatches` → Q2 matched
3. Recurrence → first claim, no blocks
4. Q2_INCENTIVE proceeds, base = ₹25,000
5. `allocateRolePercentSplit(component, [u1,u2,u3], 25000)`:
   - eligible.length = 3, not 1 → skip FULL_TO_SINGLE
   - Sort distributions by sortOrder: [FIRST_AUTHOR(0), CORRESPONDING_AUTHOR(1), REMAINDER(2)]
   - **Distribution 0**: SELECTOR_TAG "FIRST_AUTHOR", sharePercent=60 → shareAmount = 25000 * 60/100 = ₹15,000
     - `matchesDistributionSelector`: u1 has tag "FIRST_AUTHOR" → matched = [u1]
     - matchedByKey.add(u1)
     - successfulGroups.push({ FIRST_AUTHOR, [u1], 15000 })
   - **Distribution 1**: SELECTOR_TAG "CORRESPONDING_AUTHOR", sharePercent=60 → shareAmount = 25000 * 60/100 = ₹15,000
     - u1 already in matchedByKey? No — this selector checks `contributor.selectorTags.includes("CORRESPONDING_AUTHOR")`
     - u1 has ["FIRST_AUTHOR"] → no match. u2 has ["CO_AUTHOR"] → no match. u3 has ["CO_AUTHOR"] → no match.
     - recipients.length === 0, emptyShareHandling === "ROLLOVER_TO_MATCHED"
     - rolloverAmount += ₹15,000
   - **Distribution 2**: REMAINDER, sharePercent=null → shareAmount = 25000 * 0/100 = **₹0**
     - recipients = eligible NOT in matchedByKey = [u2, u3]
     - successfulGroups.push({ REMAINDER, [u2,u3], 0 })

   **❌ BUG FOUND: REMAINDER gets sharePercent=null → shareAmount = 0. The rollover of ₹15,000 goes to successfulGroups[0] (FIRST_AUTHOR), not to REMAINDER.**

   - rolloverAmount = ₹15,000 > 0 → `successfulGroups[0].amount += 15000`
   - successfulGroups[0] = { FIRST_AUTHOR, [u1], 15000 + 15000 = **₹30,000** }
   - successfulGroups[1] = { REMAINDER, [u2,u3], **₹0** }

   Final allocations:
   - u1: ₹30,000 (FIRST_AUTHOR)
   - u2: ₹0 (REMAINDER equal split of ₹0)
   - u3: ₹0 (REMAINDER equal split of ₹0)

   **Expected (Galgotia policy)**: u1 gets 60% = ₹15,000. u2 and u3 split 40% = ₹5,000 each.
   **Actual**: u1 gets ₹30,000. u2 and u3 get ₹0.

### ❌ ROOT CAUSE: Double-counting sharePercent + broken REMAINDER

Two issues:
1. **CORRESPONDING_AUTHOR distribution has sharePercent: 60, but it's a fallback — not additive.** The engine treats each distribution independently and assigns `shareAmount = baseAmount * sharePercent/100` to each. When FIRST_AUTHOR matches (60%) AND CORRESPONDING_AUTHOR doesn't match (its 60% rolls over), the rollover goes to FIRST_AUTHOR's group, making it 120% effectively — but clamped by the base amount path, it's ₹30K to first author.
2. **REMAINDER has sharePercent: null → 0 → gets ₹0.** The 40% for co-authors isn't assigned anywhere.

### ✅ FIX: Redesign the distributions for this template

The 5-case logic needs a different distribution structure. The current `allocateRolePercentSplit` processes distributions **sequentially** and rolls over empty groups to the **first successful group**. We need:

**Option A: Use only 2 distributions (no fallback for CORRESPONDING)**
```ts
distributions: [
  { selectorType: "SELECTOR_TAG", selectorTag: "FIRST_AUTHOR", sharePercent: 60, splitMode: "FULL_TO_MATCHED", sortOrder: 0 },
  { selectorType: "REMAINDER", sharePercent: 40, splitMode: "EQUAL", sortOrder: 1 },
]
```

When first author is GU → 60/40 split. When first author is external (not in eligible list) → FIRST_AUTHOR group empty → rollover to REMAINDER → REMAINDER gets 60+40 = 100% → equal split among all GU authors.

But this doesn't handle Case 3 (first author external, corresponding author GU gets 60%).

**Option B: Two-phase distribution — use CREDIT_PERCENT_SPLIT instead**

The submitter/verifier sets creditPercent based on authorship:
- Case 2/5: first author 60, co-authors split 40
- Case 3: corresponding author 60, others split 40
- Case 4: equal split (each gets 100/n)
- Case 1: sole author 100

This is the **correct approach** — the 5 cases are resolved at submission time through creditPercent assignment, not through automatic tag-based distribution.

```ts
distributionMode: "CREDIT_PERCENT_SPLIT",
distributions: [],  // no tag-based distributions needed
```

Let's re-trace with this fix:

### Scenario 4.2: Same editor, second book — should be capped at ₹20K total

**Input**: Different ISBN, same u1.

**Trace (with current R4 engine)**:
1. base = ₹15,000
2. Recurrence: RECURRING → `{ globalReason: null, blockedUserIds: {} }` → no blocks
3. u1 gets another ₹15,000

**Running total**: ₹15,000 + ₹15,000 = ₹30,000

**Expected**: ₹15,000 + ₹5,000 = ₹20,000 (capped)

**❌ BUG: R4 engine has no maxAmountPerPerson logic. The `maxAmountPerPerson: 20000` field doesn't exist in the current `RewardComponentRow` type or in `resolveComponentBaseAmount`/`resolveComponentAllocations`.**

This is an **R6.0 dependency**. Without R6.0, this template cannot enforce the ₹20K cap.

### ✅ FIX (R6.0 Task 4): After `computeRoundedAllocations`, add cap enforcement:
```
For each allocation where contributor has existing rewards for this component:
  existingTotal = SUM(finalAmount) from ContributorReward WHERE componentCode AND userId AND period
  if existingTotal + allocation.amount > maxAmountPerPerson:
    allocation.amount = max(0, maxAmountPerPerson - existingTotal)
```

### Scenario 4.3: Workaround without R6.0

Use `rewardRecurrencePolicy: "ONCE_PER_PERIOD"` instead of RECURRING. Then each editor can only claim once per period (₹15,000). This doesn't match the policy exactly (₹20K cap across multiple books) but prevents unlimited claims.

**Or** use `N_PER_PERIOD` with max=1 as a stopgap.

## Round 2: Deep-Dive Findings (Human-in-the-Loop Considered)

After second pass through the engine code, 8 additional issues were found. With a human verifier in the loop (who checks evidence, validates dates, enforces policy nuances), 5 are resolved operationally. **3 remain as engine-level bugs the verifier cannot see or prevent:**

### ❌ FIX APPLIED: Template 4 — RECURRING → ONCE_PER_UNIQUE_KEY

`buildRecurrenceKey()` returns `null` for any policy other than `ONCE_PER_UNIQUE_KEY`. So `duplicateCheckFields: ["isbn"]` had **zero effect** with RECURRING. Same ISBN could be rewarded unlimited times.

Fixed: `ONCE_PER_UNIQUE_KEY` — different ISBNs produce different keys (allowed), same ISBN produces same key (blocked).

### ❌ FIX APPLIED: Template 1 — DOI field made required

When `duplicateCheckFields: ["doi"]` and DOI is empty, `buildRecurrenceKey` returns `null`, and `evaluateRecurrence` skips blocking entirely. Same paper could be submitted and rewarded repeatedly without a DOI.

Fixed: DOI overridden to `required: true` in the GU_JOURNAL_PUB form config. Scopus/WoS journals always have DOIs.

### ❌ FIX APPLIED: Tier priority numbers reversed

`buildTierMatches` sorts ascending by priority and picks `[0]` — lowest number wins. Plan had Q1=4, Q4=1, meaning Q4 would win in any multi-match scenario.

Fixed: Q1=1 (wins), Q2=2, Q3=3, Q4=4.
