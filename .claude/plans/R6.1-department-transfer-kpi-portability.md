## Context for Codex

### What this module does

When faculty/employees transfer between departments (e.g., from Computer Science in Engineering College to IT Dept in Science College), their in-flight KPI target allocations need to be handled. The HR team decides **at transfer time** for each KPI target: does it move with the person, or stay with the old department?

### Current State

- `TransferRecord` model exists in schema with full state machine (PROPOSED → APPROVED → IN_PROGRESS → COMPLETED → CANCELLED/REJECTED)
- **No service code exists** — it's schema-only, never implemented
- `TargetAllocation` is tied to both `assignedToUnitId` (department) and `assignedToUserId` (person)
- `UserOrgAssignment` tracks which unit a user belongs to
- `ReportingLine` tracks manager-member relationships within units
- `PersonnelAction` records lifecycle events
- `TenantPersonnelPolicy` has `requireTransferApproval` flag

### Key Models

```
TransferRecord
  - membershipId → Membership (the person)
  - sourceUnitId → OrgUnit (from department)
  - targetUnitId → OrgUnit (to department)
  - status: PROPOSED → APPROVED → IN_PROGRESS → COMPLETED
  - effectiveDate, reason, newRoleDefinitionIds

TargetAllocation
  - assignedToUnitId → OrgUnit (department)
  - assignedToUserId → User (person)
  - kpiDefinitionId → KpiDefinition
  - periodId → AssessmentPeriod
  - state: ACTIVE | LOCKED
  - achievements: Achievement[]  (submitted against this target)
  - parentAllocationId → cascade lineage

UserOrgAssignment
  - versionId, unitId, userId, assignmentType (PRIMARY/SECONDARY)
  - isPrimary, effectiveFrom, effectiveTo
```

### 2c. `executeTransfer()` — The Critical Function

This runs inside a Prisma transaction when status moves to COMPLETED:

**Step 1: Move the person's org assignment**
```typescript
// Find active org structure version
const activeVersion = await tx.orgStructureVersion.findFirst({
  where: { tenantId: transfer.tenantId, status: "ACTIVE" },
});

// Update UserOrgAssignment: sourceUnitId → targetUnitId
await tx.userOrgAssignment.updateMany({
  where: {
    userId,
    unitId: transfer.sourceUnitId,
    versionId: activeVersion.id,
    assignmentType: "PRIMARY",
  },
  data: { unitId: transfer.targetUnitId },
});
```

**Step 2: Handle KPI target allocations**
```typescript
const activeTargets = await tx.targetAllocation.findMany({
  where: {
    assignedToUserId: userId,
    assignedToUnitId: transfer.sourceUnitId,
    state: "ACTIVE",
    period: { endDate: { gte: new Date() } },  // only current/future periods
  },
  include: {
    achievements: { select: { id: true, state: true } },
    kpiDefinition: { select: { title: true } },
  },
});

for (const target of activeTargets) {
  const action = resolveTargetAction(
    transfer.kpiTransferPolicy,
    transfer.kpiTransferDetails,
    target.id,
  );

  switch (action) {
    case "CARRY": {
      await tx.targetAllocation.update({
        where: { id: target.id },
        data: { assignedToUnitId: transfer.targetUnitId },
      });

      // Re-route SUBMITTED achievements to new dept's verification queue
      const submittedAchievements = target.achievements.filter(
        (a) => a.state === "SUBMITTED" || a.state === "RECOMMENDED",
      );
      if (submittedAchievements.length > 0) {
        // Add flowLog entry noting the transfer
        for (const ach of submittedAchievements) {
          await tx.achievement.update({
            where: { id: ach.id },
            data: {
              flowLog: {
                push: {
                  event: "TRANSFER_REROUTED",
                  from: transfer.sourceUnitId,
                  to: transfer.targetUnitId,
                  timestamp: new Date().toISOString(),
                },
              },
            },
          });
        }
      }

      await tx.transferTargetAction.create({
        data: {
          transferRecordId: transfer.id,
          targetAllocationId: target.id,
          action: "CARRIED",
          previousUnitId: transfer.sourceUnitId,
          newUnitId: transfer.targetUnitId,
        },
      });
      break;
    }

    case "LEAVE": {
      // Detach user — target stays in old department for reassignment
      await tx.targetAllocation.update({
        where: { id: target.id },
        data: { assignedToUserId: null },
      });

      await tx.transferTargetAction.create({
        data: {
          transferRecordId: transfer.id,
          targetAllocationId: target.id,
          action: "LEFT_BEHIND",
          previousUnitId: transfer.sourceUnitId,
          notes: `Detached from user. ${target.achievements.length} existing achievements remain. Target can be reassigned by unit head.`,
        },
      });
      break;
    }
  }
}
```

**Step 3: Handle LOCKED targets**
```typescript
// LOCKED targets cannot be carried — they belong to the period they were locked in
const lockedTargets = await tx.targetAllocation.findMany({
  where: {

```

### 2d. Helper: `resolveTargetAction()`

```typescript
function resolveTargetAction(
  policy: string | null,
  details: unknown,
  targetAllocationId: string,
): "CARRY" | "LEAVE" {
  if (policy === "CARRY_ALL") return "CARRY";
  if (policy === "LEAVE_ALL") return "LEAVE";
  // SELECTIVE
  const parsed = Array.isArray(details) ? details : [];
  const match = parsed.find((d: any) => d.targetAllocationId === targetAllocationId);
  return (match?.action as "CARRY" | "LEAVE") ?? "LEAVE";  // default: leave
}
```

## Edge Cases & Invariants

| Case | Behavior |
|------|----------|
| Transfer to same unit | Validation error — source and target must differ |
| Person has no active targets | Transfer proceeds normally, KPI section hidden in UI |
| LOCKED targets | Cannot carry — recorded as DEACTIVATED, shown as "Locked" in UI |
| Target has child allocations (cascade) | Children stay — they're unit-level. Only the user's personal target moves |
| SUBMITTED achievements when target CARRIED | Re-routed to new dept's verification queue via flowLog entry |
| VERIFIED achievements when target CARRIED | Stays as-is — already processed, rewards already calculated |
| LEFT_BEHIND target with existing achievements | Achievements stay with target. Old dept retains verification responsibility |
| LEFT_BEHIND target with no achievements | Orphaned — source unit head can reassign to another faculty |
| Transfer cancelled after APPROVED | No changes — nothing moved yet |
| Reward in PENDING state for LEFT_BEHIND target | Unaffected — reward references achievementId and contributorUserId, not unitId |
| Person is contributor on team achievement | Not affected — contributor records are per-achievement, not per-unit |
| Multiple active periods with targets | Each period's targets evaluated independently |
| Transfer during assessment period end | Show warning — suggest waiting until new period |
