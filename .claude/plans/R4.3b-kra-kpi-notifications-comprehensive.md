# R4.3b — Comprehensive KRA-KPI Notifications
# ═══════════════════════════════════════════════════════════════════════════════

## Goal

Audit ALL state transitions and user-facing events in the KRA-KPI system and ensure
every actionable event emits a notification to the right recipients. The notification
service already exists (`createNotification`, `createBulkNotifications`, `resolveUnitHead`).
This plan is about **wiring** — no new infrastructure, just adding calls at the right places.

Depends on: Existing notification-service.ts, all KRA-KPI services

---

## Locked Decisions

| # | Decision |
|---|----------|
| D1 | Notifications are **non-blocking** — if notification fails, the action still succeeds |
| D2 | Use existing `createNotification` / `createBulkNotifications` — no new service |
| D3 | Every notification includes `entityType` + `entityId` + `linkUrl` for deep linking |
| D4 | Bulk notifications (e.g., all contributors) use `createBulkNotifications` |
| D5 | Notifications are tenant-scoped — never leak across tenants |
| D6 | Self-actions do NOT generate notification to self (e.g., reporter submitting own achievement) |
| D7 | Use try/catch on all notification calls — log errors but never fail the parent operation |

### Phase 2 — Contributor Notifications (N17-N19)

**File:** `achievement-contributor-service.ts` → `setAchievementContributors`

```typescript
// After computing added/removed users:
const addedUserIds = newContributors
  .filter(c => c.type === "INTERNAL" && !existingUserIds.has(c.userId))
  .map(c => c.userId!);

const removedUserIds = existingContributors
  .filter(c => c.type === "INTERNAL" && !newUserIds.has(c.userId))
  .map(c => c.userId!);

// Filter out self (reporter shouldn't get "you were added" for their own achievement)
const reporterUserId = achievement.reportedByUserId;

if (addedUserIds.length > 0) {
  const notifyIds = addedUserIds.filter(id => id !== reporterUserId);
  if (notifyIds.length > 0) {
    await createBulkNotifications(
      tenantId, notifyIds, "CONTRIBUTOR_ADDED",
      "Added as contributor",
      `You have been listed as a contributor on "${achievement.title}"`,
      "Achievement", achievement.id, "/my-kpis"
    );
  }
}

if (removedUserIds.length > 0) {
  const notifyIds = removedUserIds.filter(id => id !== reporterUserId);
  if (notifyIds.length > 0) {
    await createBulkNotifications(
      tenantId, notifyIds, "CONTRIBUTOR_REMOVED",
      "Removed from achievement",
      `You have been removed from "${achievement.title}"`,
      "Achievement", achievement.id, "/my-kpis"
    );
  }
}
```

## Recipient Resolution Logic

| Scenario | How to Find Recipient |
|---|---|
| Verifier for submitted achievement | `resolveUnitHead(tenantId, startingUnitId)` or configured verifier |
| All contributors | `achievement.contributors.filter(c => c.type === "INTERNAL").map(c => c.userId)` |
| Reporter | `achievement.reportedByUserId` |
| OBO beneficiary | `achievement.oboReportedForUserId` |
| All allocated users in period | `targetAllocation.findMany({ where: { periodId } }).map(a => a.assignedToUserId)` |
| Admins | `membership.findMany({ where: { tenantId, role: { in: ["TENANT_ADMIN", "TENANT_OWNER"] } } })` |

## Test Scenarios

### Contributor Notifications
- T1: Add internal contributor → notification sent to them (not reporter)
- T2: Remove contributor → notification sent
- T3: Add external contributor → NO notification (no userId)
- T4: Reporter adds themselves → NO notification to self
- T5: Bulk add 3 contributors → 3 notifications (minus reporter)

### Achievement Lifecycle Notifications
- T6: Submit → verifier gets notification
- T7: Verify (approve) → reporter + all internal contributors get notification
- T8: Verify (reject) → reporter + all internal contributors get notification
- T9: Withdraw → verifier gets notification
- T10: Resubmit → verifier gets notification

### Duplicate & OBO
- T11: Submit with duplicate found → reporter gets warning notification
- T12: Submit without duplicate → no duplicate notification
- T13: OBO creation → beneficiary gets notification
- T14: Non-OBO creation → no OBO notification

### Override & Dispute
- T15: Override credit on verify → affected contributors get notification
- T16: Raise dispute → reporter + admins get notification
- T17: Resolve dispute → disputing contributor gets notification

### Edge Cases
- T18: Notification failure does NOT fail the parent operation
- T19: Cross-tenant notification isolation (user in 2 tenants, only gets notification in relevant tenant)
- T20: Self-action exclusion (reporter approving own → no self-notification)
