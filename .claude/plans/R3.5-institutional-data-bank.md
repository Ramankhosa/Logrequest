# R3.5 - Institutional Data Bank

## Goal

Build a tenant-owned institutional data bank that works even when institutional data is incomplete, inconsistent, or not yet digitized.

The tenant must be able to:
- create raw data sources
- store values or datasets in those sources
- link one source to one or many institutional metrics
- derive metrics from other metrics when needed
- use those metrics across multiple accreditation bodies without re-entering the same data repeatedly

The system must support:
- no data
- partial data
- manual estimates
- CSV-imported data
- internal-module adapters
- stale data
- conflicting data from multiple sources

And it must do that without forcing fake completeness.

## Foundational Mental Model

R3.5 should use a clear four-step chain:

```text
Data Source -> Institutional Metric -> Derived Metric -> Accreditation Block
```

Meaning:
- a **source** is raw institutional input or origin-of-truth
- a **metric** is a normalized institutional fact the institution wants to track
- a **derived metric** is computed from one or more metrics
- an **accreditation block** consumes metrics, never raw sources directly

This is the correct abstraction because:
- one source can feed many metrics
- one metric can be fed by many sources
- one metric can feed many accreditation bodies
- derived metrics can be reused across blocks and frameworks

## Current-Code Constraint

We already have:
- `SourceMetricDefinition`
- `SourceMetricObservation`
- `BlockProjectionRecipe.sourceMetricId`
- working source-metric projections
- a block-native scoring engine

So R3.5 should be additive and compatible:
- keep existing `SourceMetricDefinition` and `SourceMetricObservation` as the metric layer for v1 implementation
- add an explicit source layer above them
- keep projections and workspace runtime working
- do not force a breaking rename of current metric tables in the first pass

In this plan:
- "Institutional Metric" is the product concept
- in v1 code, it may still be implemented using the current source-metric tables plus new extensions

## Core Product Rules

1. Missing data never blocks workspace creation.
2. Unknown is not zero.
3. Partial is not complete.
4. Not applicable is not missing.
5. Raw source data and normalized metric values are different things and must not be conflated.
6. Tenant admins can create custom sources and custom metrics.
7. Metric refresh from source never silently destroys a manual or verified metric value.
8. Accreditation blocks consume metrics only, not raw sources.
9. Frozen workspaces do not auto-refresh because the data bank changed.
10. Confidence and coverage are advisory metadata, not hard blockers.

## Product Scope

### In Scope
- tenant-defined source registry
- tenant-defined metric registry
- source-to-metric links
- metric-to-metric computed dependencies
- year-wise and scope-wise observations
- scalar, dataset, narrative, document-reference values
- maturity, coverage, staleness, provenance
- manual entry
- CSV import
- adapter-backed sources from internal modules

- projection from metrics into accreditation blocks

### Out of Scope for First Build
- external government API sync
- scheduled refresh jobs

- cross-tenant benchmarking
- full evidence management redesign

## Architecture

### Layer 1: Data Sources

Data sources are raw institutional origins. Examples:
- HR faculty roster
- annual finance sheet
- placement list spreadsheet
- publication register
- IQAC narrative note
- an adapter-backed Personnel extract

Sources are not directly used by accreditation blocks. They are mapped into metrics.

### Layer 2: Institutional Metrics

Metrics are normalized institutional facts. Examples:
- `FACULTY_TOTAL`
- `FACULTY_PHD`
- `PUBLICATIONS_TOTAL`
- `PLACEMENT_RATE`
- `ANNUAL_BUDGET`

Metrics can:
- be directly entered
- be resolved from one or more sources
- be computed from other metrics

### Layer 3: Derived Metrics

Derived metrics are metrics with formula-based or aggregation-based definitions. Examples:
- `FACULTY_PHD_RATIO = FACULTY_PHD / FACULTY_TOTAL`
- `PUBLICATIONS_PER_FACULTY = PUBLICATIONS_TOTAL / FACULTY_TOTAL`
- `STUDENT_FACULTY_RATIO = STUDENT_ENROLLMENT / FACULTY_TOTAL`

### Layer 4: Accreditation Consumers

Accreditation blocks use metric values, not raw sources. This keeps the workspace layer stable and reusable across NAAC, NBA, NIRF, QS, etc.

This is the missing abstraction. It links sources to metrics.

```prisma
model MetricSourceLink {

  @@index([tenantId, metricId, isActive, precedence])

```

#### `MetricSourceLink.transformConfig` Contract

`transformConfig` must not be arbitrary JSON. It needs a documented per-mode shape.

```typescript
type MetricSourceTransformConfig =
  | { mode: "DIRECT" }
  | { mode: "PICK_FIELD"; fieldKey: string }
  | { mode: "COUNT_ROWS"; filter?: Record<string, unknown> }
  | { mode: "SUM_COLUMN"; columnKey: string; filter?: Record<string, unknown> }
  | { mode: "AVG_COLUMN"; columnKey: string; filter?: Record<string, unknown> }
  | { mode: "MAX_COLUMN"; columnKey: string; filter?: Record<string, unknown> }
  | { mode: "MIN_COLUMN"; columnKey: string; filter?: Record<string, unknown> }
  | { mode: "FIRST_NON_NULL"; fieldPriority: string[] }
  | {
      mode: "CUSTOM_FORMULA";
      formula: string;
      inputs: Array<{
        alias: string;
        source: "snapshot.numberValue" | "snapshot.textValue" | "snapshot.jsonValue" | "dataset";
        fieldKey?: string;
        columnKey?: string;
        filter?: Record<string, unknown>;
      }>;
    };
```

Rules:
- `resolutionMode` and `transformConfig.mode` must match
- `CUSTOM_FORMULA` uses the same bounded evaluator as the block engine
- row filters are declarative only, no arbitrary code
- `DIRECT` is valid only for scalar/narrative/document-ref compatible sources

## Resolution Model

### Source -> Metric

One source can feed many metrics.

Examples:
- `HR_FACULTY_MASTER` -> `FACULTY_TOTAL`
- `HR_FACULTY_MASTER` -> `FACULTY_PHD`
- `HR_FACULTY_MASTER` -> `FACULTY_BY_DEPARTMENT`

One metric can consume many sources.

Examples:
- `FACULTY_TOTAL` can come from:
  - HR roster
  - annual manually entered summary
  - imported audit sheet

### Metric -> Metric

Metrics can feed other metrics, but only through declared computed configurations.

Examples:
- `FACULTY_PHD_RATIO = FACULTY_PHD / FACULTY_TOTAL`
- `PLACEMENT_RATE = STUDENT_PLACED / GRADUATING_STUDENTS`

This graph must be cycle-checked.

### Metric -> Accreditation Block

Blocks project from metrics only. They never read raw sources directly.

This keeps:
- accreditation logic stable
- data-bank logic reusable
- projection semantics clean

## Canonical Precedence Rules

For the canonical metric value:

1. forced manual metric override
2. accepted manually entered metric value
3. accepted imported metric value
4. accepted source-linked metric value
5. accepted computed metric value
6. unknown

Important:
- source refresh may propose a better value
- but if the metric already has a manual or verified value, the refresh becomes a suggestion, not an overwrite

## Source Refresh Rules

### When Source Changes

If a source snapshot changes:
- linked metrics are identified through `MetricSourceLink`
- candidate metric values are recomputed
- if metric is unknown, candidate may auto-apply
- if metric has manual, verified, or evidence-backed value, create `MetricRefreshSuggestion`
- affected accreditation blocks are marked stale through existing projection/runtime mechanisms

### Frozen Workspace Rule

If a bank-fed metric changes after a workspace is frozen:
- metric can still be updated in data bank
- linked workspace entries are marked stale in metadata only
- no automatic response mutation or recompute

## Maturity, Coverage, and Confidence

Every source snapshot and metric observation should carry:

### Maturity
- `UNKNOWN`
- `ESTIMATED`
- `REPORTED`
- `VERIFIED`
- `EVIDENCE_BACKED`

### Coverage
- `NONE`
- `PARTIAL`
- `COMPLETE`
- `NOT_APPLICABLE`

### Confidence

Block-level score confidence should be derived from metric inputs:
- any `UNKNOWN` -> `UNSCORED`
- any `ESTIMATED` -> `LOW`
- any `PARTIAL` or `REPORTED` with no estimates -> `MEDIUM`
- all verified/evidence-backed and complete -> `HIGH`

This is advisory only.

## Adapter Design

### Adapter Principle

Adapters populate or suggest source snapshots, not raw metric overwrites.

That is the correct separation:
- adapter owns a source
- source feeds metrics
- metrics feed blocks

### Initial Internal Adapters

- Personnel
- Achievement
- KPI later

Examples:
- Personnel faculty roster source
- Achievement publication register source
- KPI annual actuals source

### Personnel Adapter Specification

Use actual fields that exist today:
- `Membership.designation`
- `Membership.dateOfJoining`
- `Membership.personnelStatus`
- `ResignationRecord`

Initial source candidates:
- `HR_FACULTY_ROSTER`
- `HR_STAFF_ROSTER`

Initial query rules:
- `FACULTY_TOTAL`: count active memberships in teaching designations
- `NON_TEACHING_STAFF_TOTAL`: count active memberships outside teaching designations
- `FACULTY_LIST`: dataset of active teaching memberships
- `FACULTY_JOINED_5YRS`: count memberships with `dateOfJoining` in last 5 years
- `FACULTY_LEFT_5YRS`: count processed separations/resignations in last 5 years

Guard:
- if required source fields do not exist, adapter returns unknown plus note, not fake zero

### Achievement Adapter Specification

Use:
- `Achievement`
- `AchievementContributor`
- `Achievement.actualValue`
- `Achievement.achievementFormData`

Initial source candidates:
- `RESEARCH_PUBLICATION_REGISTER`
- `RESEARCH_PATENT_REGISTER`
- `RESEARCH_FUNDED_PROJECT_REGISTER`

Initial query rules:
- `PUBLICATIONS_TOTAL`: count verified publication-type achievements
- `PUBLICATIONS_LIST`: dataset from publication achievements
- `PATENTS_FILED_TOTAL`: count patent-type achievements
- `FUNDED_PROJECTS_TOTAL`: count funded-project achievements
- `FUNDED_PROJECTS_AMOUNT_TOTAL`: sum `actualValue` for funded-project achievements

Guard:
- if tenant has never used the relevant achievement flow, return unknown instead of assuming zero

### KPI Adapter Specification

Deferred, but specified now so the contract is stable.

Use:
- `TargetAllocation`
- `KpiDefinition`
- achievement-backed KPI actuals where appropriate

Rules:
- only explicit metric-to-KPI mappings, no fuzzy inference
- KPI adapter writes to source layer, not directly to metric layer

## CSV Import Rules

CSV import supports:
- preview
- validate
- replace
- merge by row key

Import applies to sources first, not directly to metrics.

Why:
- spreadsheet files are raw operational data, not normalized metric decisions
- multiple metrics may be derived from the same dataset source

## Projection Integration

## Edge Cases

### E1: Tenant has no data
- source catalog can exist with zero snapshots
- metric catalog can exist with zero observations
- gap reports still work
- workspaces still function

### E2: Source exists but has no snapshot
- linked metrics remain unknown

### E3: Source has dataset but no row key
- merge imports are not allowed
- replace-only mode allowed

### E4: One source feeds multiple metrics
- each metric link resolves independently
- one dataset import can update many downstream metrics

### E5: One metric has multiple linked sources with conflicting values
- precedence decides canonical candidate
- lower-precedence value retained as source data, not metric override
- conflict note shown in preview

### E6: Manual metric value exists and source refresh changes
- create suggestion
- do not overwrite

### E7: Verified metric edited manually
- maturity resets to reported
- verification metadata cleared

### E8: Verified source changes
- linked metrics may become stale
- verified metric values still not overwritten automatically

### E9: Computed metric has one unknown input
- result null
- maturity unknown

### E10: Computed metric denominator is zero
- result null
- evaluation note recorded

### E11: Computed metric cycle
- reject at create/update time
- runtime still has max-depth guard

### E12: Source deactivated while metric links exist
- block deactivation unless links are removed or replaced

### E13: Metric deactivated while blocks project it
- block deactivation or recipe reassignment required first

### E14: Dataset source only covers some departments
- source coverage partial
- linked metric may still compute aggregate
- aggregate marked partial

### E15: Body needs 5 years but only 3 years exist
- missing years remain unknown
- scoring uses what exists and nulls what does not

### E16: Metric is not applicable to institution
- mark not applicable
- exclude from gaps
- prevent unnecessary warnings

### E17: Multiple accreditation bodies use same metric with different semantics
- same raw metric can be reused
- body-specific interpretation stays in accreditation layer, not data-bank layer

### E18: Source schema changes after metric links were configured
- link preview goes invalid
- affected links marked broken
- no silent remapping

### E19: Source imported twice with different column names
- preview suggests mapping
- user confirms before apply

### E20: Adapter source module unused by tenant
- result stays unknown
- never fake zero unless operationally proven zero

### E21: Frozen workspace linked to stale metric
- show stale indicator
- no automatic recompute

### E22: Two sources both primary for one metric
- reject configuration

### E23: Metric derives from other derived metrics
- allowed
- cycle detection and depth guard mandatory

### E24: Dataset source feeds both count metric and ratio metric
- count metric aggregates rows
- ratio metric can depend on count metric and another metric
- no duplicate data entry required
