# R5.0 — Role Fixes + Hierarchy Scope Engine

**Assigned to**: Codex (backend-only, no UI)
**Depends on**: Nothing (first sub-module)
**Blocks**: All R5.1–R5.6 sub-modules

---

## Why This Exists

The org hierarchy and roles are well-structured in the schema, but two critical fields (`scope` and `approvalAuthority`) are stored but never enforced. All R5 dashboard modules depend on knowing "what units can this user see?" — which requires these fields to actually work. This sub-module activates them and builds the reusable hierarchy utilities that every dashboard query will use.

## ⚠ Codex Review Fixes Applied (8 findings addressed)

**Finding 2 (HIGH)**: Scope model was incomplete — users can belong to a unit via `UserOrgAssignment` without any `OrgRoleAssignment`. The scope resolver in Task 5 now ALSO queries `UserOrgAssignment` for the user's units, not just role assignments.

**Finding 3 (HIGH)**: Simple `assignedToUnitId IN scopeUnitIds` filter was insufficient. The dashboard has two allocation patterns: (a) allocations assigned to a unit directly, and (b) allocations assigned to a user whose primary unit is in scope. Task 6 now uses a shared `buildEffectiveUnitFilter()` strategy that handles BOTH patterns.

**Finding 7 (MEDIUM)**: All hierarchy queries MUST include `versionId` (the PUBLISHED version) to avoid mixing draft/published units. Tenant admins get `rootScopeUnits` = level-0 root units (not empty).

## Task 4: Create hierarchy utility functions

**New file**: `src/lib/org-structure/hierarchy-utils.ts`

### 4a. `getDescendantUnitIds(tenantId, rootUnitId, includeRoot?): Promise<string[]>`
- First resolve the PUBLISHED `versionId` via `getActiveVersionId(tenantId)` (already exists in personnel/service.ts)
- Get the root unit's `path` from DB
- If `path` exists: `WHERE tenantId = X AND versionId = V AND path LIKE '{rootPath}/%'` (fast)
- If `path` is null: BFS traversal using `parentId` with `versionId` filter (fallback)
- `includeRoot` defaults to `true`
- **CRITICAL**: ALL queries MUST include `versionId` to avoid mixing draft/published units (Finding 7)

### 4b. `getSubtreeUnitIds(tenantId, rootUnitIds[]): Promise<string[]>`
- Calls `getDescendantUnitIds` for each root, returns deduplicated union
- Used when a user heads multiple units

### 4c. `getAncestorChain(tenantId, unitId): Promise<{id, name, code, level, category}[]>`
- Walk UP the tree via `parentId` from the given unit to root
- Return array ordered from root to unit (for breadcrumb display)
- Include unit type category for each level

### 4d. `getSiblingUnits(tenantId, unitId): Promise<{id, name, code, category}[]>`
- Find the unit's `parentId`
- Return all units with the same `parentId` (excluding the given unit)
- Used for cross-unit comparison at the same level

### Checklist
- [ ] `getDescendantUnitIds` works with path-based query (fast path)
- [ ] `getDescendantUnitIds` works with BFS fallback when path is null
- [ ] `getSubtreeUnitIds` deduplicates across multiple roots
- [ ] `getAncestorChain` returns root-to-unit order
- [ ] `getSiblingUnits` excludes the given unit from results
- [ ] **ALL functions include `versionId` filter — never query without it (Finding 7)**
- [ ] All functions use the PUBLISHED org structure version (call `getActiveVersionId`)
- [ ] All functions are exported and have JSDoc comments

## Task 5: Create scope resolver

**New file**: `src/lib/org-structure/scope-resolver.ts`

### 5a. `resolveUserDashboardScope(tenantId, userId): Promise<UserDashboardScope>`

```typescript
type UserDashboardScope = {
  userId: string;
  tenantId: string;
  isTenantAdmin: boolean;
  headOfUnits: { unitId: string; unitName: string; unitCode: string; scope: 'NODE' | 'DESCENDANTS' }[];
  memberOfUnits: { unitId: string; unitName: string; unitCode: string }[];
  hasApprovalAuthority: boolean;
  visibleUnitIds: string[] | 'ALL';
  rootScopeUnits: { unitId: string; unitName: string; unitCode: string; category: string }[];
};
```

**Logic**:
1. Call `getUserAssignments(tenantId, userId)` to get all role assignments
2. **Also query `UserOrgAssignment`** for the user's units (published version only) — this captures users who belong to a unit without any org role (Finding 2):
   ```ts
   const userUnits = await prisma.userOrgAssignment.findMany({
     where: { userId, version: { tenantId, state: 'ACTIVE' } },
     select: { unitId: true, unit: { select: { name: true, code: true } } }
   });
   ```
3. Check tenant role (from session/DB) — if `TENANT_OWNER` or `TENANT_ADMIN`:
   - Set `isTenantAdmin = true`, `visibleUnitIds = 'ALL'`
   - **Set `rootScopeUnits` = all level-0 root units in the published version** (Finding 7 — admins need root entry points for R5.4 drill-down)
4. For non-admin users:
   - Collect `headOfUnits` from assignments where `isUnitHead = true`, include `scope`
   - For each head-of-unit:
     - If `scope = 'NODE'` → add that unitId to `visibleUnitIds`
     - If `scope = 'DESCENDANTS'` → call `getDescendantUnitIds(tenantId, unitId, true)` → add all to `visibleUnitIds`
   - **Also add all units from `UserOrgAssignment` query** (not just role-based memberOfUnits) — a user can always see their own unit's data even if they hold no org role (Finding 2)
   - Deduplicate `visibleUnitIds`
5. `rootScopeUnits` = the headOfUnits entries (these are the top-level entry points for the Organization tab)
6. `hasApprovalAuthority` = true if any assignment has `approvalAuthority = true`

### 5b. `applyScopeFilter(baseWhere, scope, unitIdField): object`
- If `scope.visibleUnitIds === 'ALL'` → return `baseWhere` unchanged
- Otherwise → return `{ ...baseWhere, [unitIdField]: { in: scope.visibleUnitIds } }`
- This is a helper used by all dashboard service functions

### Checklist
- [ ] `resolveUserDashboardScope` correctly identifies tenant admin
- [ ] **Tenant admin `rootScopeUnits` = level-0 root units, NOT empty (Finding 7)**
- [ ] NODE scope adds only that unit
- [ ] DESCENDANTS scope adds entire subtree
- [ ] **Users with `UserOrgAssignment` but no `OrgRoleAssignment` still get their units in `memberOfUnits` and `visibleUnitIds` (Finding 2)**
- [ ] `visibleUnitIds` is deduplicated
- [ ] `rootScopeUnits` gives the correct entry points for drill-down
- [ ] `hasApprovalAuthority` is correctly derived
- [ ] `applyScopeFilter` is a no-op when scope is `'ALL'`

## Task 6: Add scope filtering to existing dashboard service

**Modify**: `src/lib/kra-kpi/dashboard-service.ts`

### 6a. Create shared "effective allocation unit" filter strategy (Finding 3)

The dashboard has TWO allocation patterns:
- (a) `TargetAllocation.assignedToUnitId` — allocation assigned directly to a unit
- (b) `TargetAllocation` assigned to a user whose **primary unit** is in scope (user-level allocations)

A simple `assignedToUnitId IN scopeUnitIds` misses pattern (b). Create a shared helper:

```typescript
function buildEffectiveUnitFilter(scopeUnitIds: string[] | 'ALL') {
  if (scopeUnitIds === 'ALL') return {};
  return {
    OR: [
      { assignedToUnitId: { in: scopeUnitIds } },
      {
        assignedToUserId: { not: null },
        assignedToUser: {
          orgAssignments: {
            some: {
              unitId: { in: scopeUnitIds },
              assignmentType: 'PRIMARY'
            }
          }
        }
      }
    ]
  };
}
```

This ensures both unit-level AND user-level allocations are captured when filtering by scope.

### 6b. Add scope parameter to all 6 functions

Add an optional `scopeUnitIds?: string[] | 'ALL'` parameter to ALL existing public functions:
- `getOverviewStats(tenantId, periodId, scopeUnitIds?)`
- `getOrgHierarchyStats(tenantId, periodId, parentUnitId?, scopeUnitIds?)`
- `getAttentionItems(tenantId, periodId, scopeUnitIds?)`
- `getStageBottleneckAnalysis(tenantId, periodId, kpiId, scopeUnitIds?)`
- `getKpiCrossComparison(tenantId, periodId, kpiId, scopeUnitIds?)`
- `getPersonDetail(tenantId, periodId, userId, scopeUnitIds?)`

**How**: In each function's Prisma query, use `buildEffectiveUnitFilter(scopeUnitIds)` to add the combined WHERE clause.
