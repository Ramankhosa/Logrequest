## Context for Codex

### What are KPI Templates?

KPI Templates are pre-configured KPI definitions stored in the `KpiTemplate` table with `isSystem = true, tenantId = null`. Orgs import them via `applyTemplateToKpi()` which seeds benefit types, contributor roles, form fields, tiers, components, and distributions.

### How templates work

```
KpiTemplate (DB)
  ├─ code: unique string (e.g., "GU_SCOPUS_JOURNAL_PUBLICATION")
  ├─ name: display name
  ├─ category: "GALGOTIA_RD"
  ├─ isSystem: true
  ├─ tenantId: null
  └─ builderPayload: JSON → KpiBuilderPayload Zod schema
       ├─ definition: BuilderKpiDefinition (measurement, scoring, form config, recurrence, etc.)
       ├─ applicableRoles: BuilderApplicableRole[]
       ├─ contributorConfig: BuilderContributorConfig
       ├─ stages: BuilderStage[] (usually empty for R&D incentives)
       ├─ rewardTiers: BuilderRewardTier[] (each with rules[])
       └─ rewardComponents: BuilderRewardComponent[] (each with distributions[])
```

### Placeholder values

All templates use these placeholders that `applyTemplateToKpi()` overrides at import time:
- `kraDefinitionId: "TEMPLATE_KRA"`
- `startingUnitId: "TEMPLATE_UNIT"`

| `Q4_INCENTIVE` | `Q4` | `amountValue: 10000` | `CREDIT_PERCENT_SPLIT` |

#### Distribution Logic — The 5 Galgotia Cases (from policy sheet)

The policy defines a **fixed 5-case matrix** for author incentive splitting:

| Case | First Author (GU) | Corresponding Author (GU) | Co-Authors (GU) | Total Paid |
|---|---|---|---|---|
| Case 1 | 35% | 35% | 30% (equal split) | 100% |
| Case 2 | 50% | 50% | — | 100% |
| Case 3 | 60% (first OR corresponding) | — | 40% (equal split) | 100% |
| Case 4 | 100% (first OR corresponding) | — | — | 100% |
| Case 5 | — (external) | — (external) | 40% (equal split) | **40% only** |

Additional policy rules:
- "If multiple co-authors/corresponding from GU, then same respective amount will equally distribute among all."
- PhD scholars/supervisors entitled for incentives only on papers **beyond their minimum publication for PhD Program**.
- In case of multiple quartiles, higher quartile of Scopus/WoS will be considered.

**Implementation Strategy**: Use `CREDIT_PERCENT_SPLIT` distribution mode. The verifier sets `creditPercent` on each GU contributor based on which case applies.

> ⚠️ **Simulation finding**: ROLE_PERCENT_SPLIT with fallback CORRESPONDING_AUTHOR tag was originally considered but **fails** — the engine processes distributions sequentially and the fallback creates double-counting. See `R6.2-galgotia-template-simulations.md` Scenario 1.2 for full trace.

**CREDIT_PERCENT_SPLIT** handles Cases 1-4 correctly. The verifier identifies the case and sets creditPercent:

| Case | Who sets creditPercent | Example (₹30K Q1) |
|---|---|---|
| Case 1 | First=35%, Corresponding=35%, Co-authors split 30% | 3 co-authors: FA=35%, CA=35%, co1=10%, co2=10%, co3=10% |
| Case 2 | First=50%, Corresponding=50% | FA=50%, CA=50% → ₹15K each |
| Case 3 | First/Corresponding=60%, Co-authors split 40% | FC=60%, co1=20%, co2=20% → ₹18K, ₹6K, ₹6K |
| Case 4 | First/Corresponding=100% | FC=100% → ₹30K |
| Case 5 | **⚠️ Engine limitation** — see below | Co-authors only, 40% of tier amount |

> **Case 5 limitation**: The engine normalizes `creditPercent` to pay 100% of `baseAmount`. When only co-authors are eligible (no first/corresponding from GU), the policy says only 40% should be paid — but the engine will pay the full tier amount split among co-authors. **Verifier must manually adjust DRAFT reward amounts** for Case 5 before releasing. This is rare (requires both first author AND corresponding author to be external while GU has only co-authors).

**Component config for all 4 components**:
```ts
distributionMode: "CREDIT_PERCENT_SPLIT",
singleEligibleHandling: "FULL_TO_SINGLE",
emptyShareHandling: "ROLLOVER_TO_MATCHED",
distributions: [],  // no tag-based distributions — creditPercent handles Cases 1-4
```

#### Edge Cases

1. **External authors are excluded** from incentive — only GU employees get rewards. External contributors are added to the achievement for record-keeping but `isExcludedFromReward: true`.
2. **Duplicate DOI check** — `duplicateCheckFields: ["doi"]` prevents same paper being claimed twice. DOI is `required: true`.
3. **Full-time faculty only** — policy states "author must be a regular faculty of GU" and "full-time faculty of GU/full time PhD Scholar". R6.0's CONTRIBUTOR_TAG source can add a tier rule for employmentType. For now, verifier enforces.
4. **PhD minimum publication threshold** — policy says PhD scholars/supervisors only get incentives on papers "beyond their minimum publication for PhD Program". This is a threshold check the verifier handles. Cannot be automated without knowing each scholar's minimum count.
5. **Multiple quartile match** — policy says "higher quartile of Scopus/WoS will consider". Tier priority ensures Q1 (priority 1) wins over Q4 (priority 4).
6. **Case 5 payout** — only 40% of tier amount should be paid. Engine limitation; verifier adjusts DRAFT amounts.

### Template 4: GU_SCOPUS_EDITED_BOOK

**Galgotia Policy**: Scopus-indexed edited book. ₹15,000 per book.

**₹20K Cap (from policy image)**: "In case of edited book, editor will get maximum of Rs. 20,000 as an editor's incentives plus author of one or multiple chapters in the same book."

This is a **same-ISBN cross-template cap**: if a person is editor of a book (₹15K from this template) AND also authored chapters in the same book (₹5K each from Template 5), the combined total for that ISBN is capped at ₹20K. This is NOT a cross-book annual cap.

> **R6.2 approach**: This is a cross-KPI aggregate check that the engine cannot enforce automatically. The **verifier** checks whether the same contributor has claims across edited-book and book-chapter templates for the same ISBN, and ensures the combined total doesn't exceed ₹20K. ## Edge Cases & Deviations

### 1. External vs Internal Author Handling
**Issue**: Galgotia policy explicitly says incentives are for GU faculty only. External co-authors should NOT receive rewards.
**Solution**: `allowExternalContributors: true` (for record-keeping) but external contributors have `isExcludedFromReward: true`. The reward engine already respects this flag in `getEligibleContributors()`.

### 2. Edited Book ₹20K Cap (#4 + #5)
**Issue**: Policy says "editor will get maximum of Rs. 20,000 as an editor's incentives plus author of one or multiple chapters in the same book." This is a same-ISBN cross-template cap: editor incentive (₹15K) + chapter incentives (₹5K each) for the same ISBN, capped at ₹20K total.
**Solution**: Verifier checks whether the same contributor has claims across the edited-book and book-chapter templates for the same ISBN, and ensures combined total ≤ ₹20K. No engine change needed.

### 3. Semester-Based Period for Conference Papers (#12)
**Issue**: "Max 2 per semester" — the system needs to know what "semester" means for this org.
**Solution**: Period is defined at the KPI allocation level (TargetAllocation has start/end dates). `N_PER_PERIOD` counts achievements within the allocation period. When an org imports this template, they set semester dates on their allocation.

### 4. "No University Financial Support" Gate (#12)
**Issue**: Conference paper claims require that the faculty did NOT receive university funding.
**Solution**: Boolean form field `receivedUniversityFunding` + tier rule `eq false`. Verifier also checks this.

### 5. Consultancy "Savings" Calculation (#8, #13)
**Issue**: Policy says "70% of savings". Savings = Revenue - Expenditure. This is a derived value.
**Solution**: Three form fields: `projectValue`, `totalExpenditure`, `savings`. The submitter calculates savings. Verifier validates. The `PERCENT_OF_FIELD` references `savings` directly. Future enhancement: computed fields in form config.

### 6. EDP/MDP "Distribution Chart" (#13)
**Issue**: Policy says "convenor submits distribution chart".
**Solution**: Maps to `CREDIT_PERCENT_SPLIT` — the convenor adds each team member as a contributor with their agreed `creditPercent`. This IS the distribution chart. Evidence attachment can include the signed chart document.

### 7. Patent "GU as Applicant" Gate (#9)
**Issue**: Patent incentive only if Galgotia University is the applicant.
**Solution**: Boolean form field `applicantIsGU` + tier rule gating on `true`. Verifier confirms from patent document.

### 8. Duplicate Prevention
**Issue**: Same publication/patent/grant should not be claimed by multiple people independently.
**Solution**: `duplicateCheckFields` on each template — DOI for journals, ISBN for books, applicationNumber for patents, sanctionNumber for grants, etc. The system's existing duplicate detection will flag these.

### 9. Solo Author/Inventor/PI Handling
**Issue**: When there's only one eligible internal person, they should get 100%.
**Solution**: `singleEligibleHandling: "FULL_TO_SINGLE"` on all components. This is already the default.

### 10. Co-Supervisor Split (#6)
**Issue**: 40% split among multiple co-supervisors equally.
**Solution**: Distribution with `selectorTag: "CO_SUPERVISOR"`, `sharePercent: 40`, `splitMode: "EQUAL"`. If 2 co-supervisors, each gets 20%.
