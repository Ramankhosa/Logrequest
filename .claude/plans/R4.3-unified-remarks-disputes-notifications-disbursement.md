# R4.3 Fresh — Workflow Remarks, Notifications, Audit Trail, Corrections, and Reward Operations

## Status
- Canonical R4.3 plan and implementation note
- Implemented on `2026-03-24`
- Replaces the older R4.3a / R4.3b split plans and folds the planned reward-disbursement work into the same slice

## Scope
Build on the existing KRA/KPI workflow without redesigning:
- submission
- recommendation
- final verification
- source/key/final division routing
- dashboards and review queues
- in-app notification stack

Add the missing operational features:
- remarks at submit / recommend / reject / verify / correct / revoke
- richer user-facing workflow timeline via `SubmissionTrail`
- idempotent notification delivery for workflow and reward events
- final-approver / tenant-admin correction of verified achievements
- reward lifecycle management: `DRAFT`, `PENDING`, `RELEASED`, `REVOKED`
- reward operations console with history, filters, totals, and bulk transitions
- immutable handling for released rewards with revoke-and-replace semantics

## Frozen decisions
- `SubmissionTrail` is the canonical product timeline. No second workflow-history table.
- `auditLog` remains the system audit source. It complements `SubmissionTrail`.
- Workflow states stay unchanged. Verified corrections do not reopen the approval chain.
- Remarks are required for reject, correct, and revoke actions.
- Notifications are in-app only and non-blocking.
- Notification unread counts are not the source of truth for pending work. Pending review indicators come from live queue queries.
- Reward rows are never hard-deleted.
- Released rewards are immutable in amount/identity. Corrections revoke old rows and create replacement draft rows when still eligible.
- Reward reporting uses reward-time org snapshots on `ContributorReward`, not only live org hierarchy.
- Reward console is admin-only in this phase.

## Implemented submodules
### 1. Workflow remarks and timeline enrichment
- Reused `SubmissionTrail`
- Added/used actions:
  - `SUBMITTED`
  - `RESUBMITTED`
  - `RECOMMENDED`
  - `REJECTED`
  - `VERIFIED`
  - `WITHDRAWN`
  - `CORRECTED`
  - `REWARD_RECALCULATED`
  - `REWARD_REVOKED`
  - `REWARD_RELEASED`
  - `REWARD_MARKED_PENDING`
- `SubmissionTrail.metadata` now carries structured correction/reward context:
  - `changedFieldKeys`
  - `beforeAfterSummary`
  - `correctionReason`
  - `oldState`
  - `newState`
  - reward recalculation counts where relevant
- Existing summary fields on `Achievement` remain in use for quick display:
  - `recommendationNote`
  - `verificationNote`
  - `rejectionReason`

### 2. Notification hardening
- Reused `createNotification` and `createBulkNotifications`
- Added `Notification.eventKey`
- Enforced uniqueness per `(tenantId, userId, eventKey)`
- Added deduped workflow/reward notification event keys for:
  - submit
  - recommend
  - reject
  - verify
  - correction
  - reward pending
  - reward released
  - reward revoked

### 3. Verified correction flow
- Added a dedicated verified-correction path in `achievement-service`
- Authorized actors:
  - final approver within scope
  - tenant admin / tenant owner / superadmin
- Correction:
  - keeps the achievement in `VERIFIED`
  - appends `SubmissionTrail`
  - writes `auditLog`
  - recomputes duplicate checks and derived scores
  - triggers reward refresh when reward-affecting data changes
- Partial `achievementFormData` updates are merged with existing form data before validation and persistence

### 4. Reward ledger evolution
- `ContributorRewardState` is now:
  - `DRAFT`
  - `PENDING`
  - `RELEASED`
  - `REVOKED`
- Added operational fields on `ContributorReward`:
  - `statusRemark`
  - `releasedAt`, `releasedById`, `releaseReference`
  - `revokedAt`, `revokedById`, `revocationReason`
  - `supersedesRewardId`, `replacedByRewardId`
  - reward-owner and reporter org snapshots for stable reporting filters
- Added append-only `ContributorRewardEvent`

### 5. Reward recalculation and state transitions
- Reward recalculation after verified correction:
  - updates or recreates `DRAFT` / `PENDING` rows
  - revokes `RELEASED` rows instead of mutating them
  - creates replacement `DRAFT` rows when still eligible
  - preserves revoke/replace lineage even when the reward component changes across tiers
- Reward transition service supports:
  - `DRAFT -> PENDING`
  - `DRAFT -> RELEASED`
  - `PENDING -> RELEASED`
  - `DRAFT/PENDING/RELEASED -> REVOKED`
- Revoke requires a remark
- Transitions are transactional and state-guarded

### 6. UI delivery
- Applicant surfaces:
  - submission remark input
  - `SubmissionTrail` timeline rendering
- Reviewer / approver surfaces:
  - timeline rendering
  - review-state badges
  - verified-correction action path
- Admin surfaces:
  - reward operations console
  - filterable reward table
  - grouped totals by benefit type
  - reward event history
  - bulk pending / release / revoke actions

## Non-goals / deferred items
- no dispute workflow engine
- no credit-override-at-verification feature
- no stage-triggered reward release
- no finance-only approval layer
- no email / SMS / push notification channels
- no workflow-state redesign
