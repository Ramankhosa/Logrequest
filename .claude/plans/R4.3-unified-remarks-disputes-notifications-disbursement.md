# ═══════════════════════════════════════════════════════════════════════════════

## Overview

Merges three remaining R4 items into one implementation:
- **Part A** — Applicant remarks, verifier credit override, contributor dispute
- **Part B** — Comprehensive notification wiring (23 events)
- **Part C** — Reward approval & disbursement tracking (extend ContributorReward)

**Replaces:** R4.3a, R4.3b, and the new R4.4 (approval/disbursement)

**Complexity:** Medium — no new tables, ~15 new columns, extends existing services

**Dependencies:** R4.1a-c ✅, R4.2 ✅ (all done)

## Locked Decisions

| # | Decision |
|---|----------|
| D1 | `remarks` is a free-text field on Achievement — applicant-facing, visible to reviewers |
| D2 | Verifier credit override stores: who overrode, original values, reason (mandatory) |
| D3 | Override is ONLY available to the **final verifier** at verification time — not recommenders |
| D4 | Override creates an audit trail — original credits preserved in `creditOverrideSnapshot` JSON |
| D5 | After override, inline shadow field `Achievement.creditPercent` syncs to reporter's new value |
| D6 | Dispute is a lightweight flag on AchievementContributor — not a separate workflow engine |
| D7 | Dispute can only be raised on VERIFIED achievements (post-approval) |
| D8 | Disputed achievements appear in admin review queue with a badge |
| D9 | Dispute resolution is manual — admin/verifier updates contributor record and clears flag |
| D10 | Remarks field is editable in DRAFT and REJECTED states only (same as other achievement fields) |
| D11 | Notifications are **non-blocking** — if notification fails, the action still succeeds |
| D12 | Use existing `createNotification` / `createBulkNotifications` — no new notification service |
| D13 | Every notification includes `entityType` + `entityId` + `linkUrl` for deep linking |
| D14 | Self-actions do NOT generate notification to self |
| D15 | External contributors (no userId) do NOT receive notifications |
| D16 | Reward state machine: `CALCULATED → APPROVED → DISBURSED`, or `CALCULATED → CANCELLED`, or `APPROVED → CANCELLED` |
| D17 | Only TENANT_ADMIN / TENANT_OWNER can approve or disburse rewards |
| D18 | Disbursement records a `transactionRef` for external payment system tracking |
| D19 | Reward recalculation after credit override: if credits change during dispute resolution, call `syncContributorRewardsForAchievement` again (idempotent via idempotencyKey) |
| D20 | Credit override at verification time happens BEFORE reward calculation — so the reward engine uses the overridden credits |

## Part A — Service Changes

### 1. `achievement-service.ts` — Add remarks to record + update

**In `createAchievementSchema`:** Add `remarks: z.string().trim().max(2000).optional()`

**In `recordAchievement`:** Pass `remarks` to `prisma.achievement.create` data.

**In `updateAchievement`:** Pass `remarks` to update data. Validation: only editable when `state === "DRAFT" || state === "REJECTED"` (already enforced by the existing state check).

### 2. `achievement-service.ts` — Extend `verifyAchievement` with credit overrides

**Extended signature:**
```typescript
export async function verifyAchievement(
  achievementId: string,
  tenantId: string,
  approved: boolean,
  note: string | null,
  actorUserId: string,
  actorRole: Role,
  creditOverrides?: Array<{
    contributorId: string;
    newCreditPercent: number;
  }>,
): Promise<KraKpiActionResult>
```

**Override logic — execute BEFORE reward calculation, inside the verification transaction:**

1. Validate all `contributorId` values belong to this achievement
2. Validate each `newCreditPercent` is >= 0
3. If any overrides provided, `note` becomes mandatory (reject if missing)
4. For each override:
   - Save `originalCreditPercent` = current `creditPercent`
   - Update `creditPercent` to new value
   - Set `creditOverriddenBy`, `creditOverrideReason`, `creditOverriddenAt`
5. Build and save `creditOverrideSnapshot` JSON on Achievement:
   ```json
   [
     { "contributorId": "...", "userId": "...", "originalCredit": 60, "newCredit": 50 },
     { "contributorId": "...", "userId": "...", "originalCredit": 40, "newCredit": 50 }
   ]
   ```
6. Set `Achievement.creditOverriddenBy` and `Achievement.creditOverrideReason` (denormalized)
7. Sync inline shadow: if reporter's contributor row was overridden, update `Achievement.creditPercent`

**IMPORTANT ordering:** Overrides happen inside the transaction BEFORE `syncContributorRewardsForAchievement` is called, so the reward engine picks up the overridden credit values.

### 3. `achievement-contributor-service.ts` — Add dispute functions

**New exports:**

```typescript
export async function raiseDispute(
  contributorId: string,
  tenantId: string,
  note: string,
  actorUserId: string,
): Promise<KraKpiActionResult>
```

Logic:
1. Load contributor with achievement
2. Verify `contrib.userId === actorUserId` (only the contributor themselves)
3. Verify `achievement.state === "VERIFIED"` (disputes only on verified)
4. Verify `disputeStatus !== "DISPUTED"` (no double disputes)
5. Update: `disputeStatus = "DISPUTED"`, `disputeNote = note`, `disputedAt = now()`
6. Create audit log entry
7. Send notifications (reporter + admins)

```typescript
export async function resolveDispute(
  contributorId: string,
  tenantId: string,
  resolutionNote: string,
  actorUserId: string,
  actorRole: Role,
  newCreditPercent?: number,
): Promise<KraKpiActionResult>
```

Logic:
1. Verify admin/owner role
2. Verify `disputeStatus === "DISPUTED"`
3. Update: `disputeStatus = "RESOLVED"`, resolution fields set
4. If `newCreditPercent` provided:
   - Save `originalCreditPercent` snapshot
   - Update `creditPercent`
   - Set override fields
   - Call `syncContributorRewardsForAchievement` to recalculate rewards with new credits (idempotent)
5. Create audit log entry
6. Send notification to disputing contributor

### State Machine

```
CALCULATED ──→ APPROVED ──→ DISBURSED
    │              │
    └──→ CANCELLED ←┘
```

**`approveRewards` logic:**
1. Verify admin/owner role
2. Load rewards, verify all belong to tenant and state = "CALCULATED"
3. Update each: `state = "APPROVED"`, `approvedByUserId`, `approvedAt`, `remarks`
4. Audit log
5. Notify each reward recipient (N23)

**`disburseRewards` logic:**
1. Verify admin/owner role
2. Load rewards, verify all state = "APPROVED"
3. Require `transactionRef` (non-empty)
4. Update each: `state = "DISBURSED"`, `disbursedByUserId`, `disbursedAt`, `transactionRef`, `remarks`
5. Audit log
6. Notify each recipient (N24)

**`cancelRewards` logic:**
1. Verify admin/owner role
2. Load rewards, verify state is "CALCULATED" or "APPROVED" (cannot cancel already disbursed)
3. Require `reason`
4. Update each: `state = "CANCELLED"`, `cancelledByUserId`, `cancelledAt`, `cancelledReason`
5. Audit log
