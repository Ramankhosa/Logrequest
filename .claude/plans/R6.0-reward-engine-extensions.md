## Context for Codex

### What is this project?

LogRequest is a multi-tenant KRA/KPI performance management platform built with **Next.js 15 (App Router) + Prisma + PostgreSQL**. It lets organizations define KRAs (Key Result Areas), each containing KPIs (Key Performance Indicators). Faculty/employees submit "Achievements" against KPIs, which go through a verification workflow, and upon verification, a **reward calculation engine** computes incentives (monetary or otherwise) and distributes them among contributors.

### How the reward engine currently works

The reward engine lives in **`src/lib/kra-kpi/reward-service.ts`** (~1400 lines). Here's the pipeline:

```
Achievement VERIFIED
        │
        ▼
loadRewardConfig()          → Loads KpiDefinition + tiers + components + distributions from DB
        │
        ▼
resolveRewards()            → Main orchestrator, calls everything below:
  ├─ resolvePolicyDate()    → Determines the effective date for time-window checks
  ├─ buildRecurrenceKey()   → Builds duplicate-check key from configured fields
  ├─ normalizeContributors()→ Standardizes contributor records
  ├─ getEligibleContributors()→ Filters out excluded contributors
  ├─ buildTierMatches()     → Evaluates tier rules to find matching tiers
  │   └─ resolveRuleSourceValue() → Gets the value to compare (form field, score, metric, etc.)
  │   └─ evaluateOperator()       → Runs the comparison (eq, gt, contains, has_any, etc.)
  ├─ evaluateRecurrence()   → Checks if reward already claimed (ONCE_PER_PERIOD, etc.)
  │
  └─ FOR EACH rewardComponent:
      ├─ resolveComponentBaseAmount() → Calculates base amount (FIXED_VALUE, PERCENT_OF_FIELD, etc.)
      ├─ resolveComponentAllocations()→ Splits amount among contributors (EQUAL_SPLIT, ROLE_PERCENT_SPLIT, etc.)
      └─ computeRoundedAllocations() → Applies rounding + marks blocked users from recurrence
        │
        ▼
buildPersistableRows()      → Creates ContributorReward records with explanation JSON
```

### Key models (Prisma schema)

- **`KpiDefinition`** — defines a KPI, holds `rewardRecurrencePolicy`, `achievementFormConfig` (dynamic form schema), and references `KpiRewardTier[]` + `KpiRewardComponent[]`
- **`KpiRewardTier`** — a named tier (e.g., "Q1 Journal", "Q2 Journal") with `KpiRewardRule[]` that gate it (e.g., `formField:quartile eq "Q1"`)
- **`KpiRewardRule`** — a single condition: `source` (String), `operator` (String), `fieldKey`, `value` (Json)
- **`KpiRewardComponent`** — a reward line item (e.g., "Author Incentive ₹30K"). Has `amountMode` (FIXED_VALUE, PERCENT_OF_FIELD, etc.), `distributionMode` (EQUAL_SPLIT, ROLE_PERCENT_SPLIT, etc.), optional tier binding, and `KpiRewardDistribution[]`
- **`KpiRewardDistribution`** — how to split a component among contributors by role/tag
- **`ContributorReward`** — persisted reward record per contributor, with `baseAmount`, `finalAmount`, `explanation` (JSON audit trail), `state` (DRAFT→PENDING→RELEASED), `recurrenceKey`
- **`Achievement`** — a submitted + verified achievement with `achievementFormData` (JSON, dynamic), `contributors` (AchievementContributor[])
- **`AchievementContributor`** — a person on an achievement, has `selectorTags` (String[]), `contributorRoleId`, `creditPercent`

### What R6.0 adds and why

Field testing against real university incentive policies (Galgotia University's 13-item policy, and similar) revealed **3 structural gaps** in the reward engine that block ~25% of real-world policy rules:

1. **No reward caps** — "editor gets max ₹20,000" can't be enforced
2. **No threshold/floor** — "incentive only on papers *beyond* the minimum for PhD program" can't be expressed
3. **No N-per-period frequency** — "max 2 conference paper claims per semester" can't be enforced

Plus one eligibility gap:
4. **No contributor-level rule sources** — "must be full-time faculty" can't be checked in tier rules (only form fields and scores were supported)

And one submission UX gap:
5. **No self-declaration/attestation fields** — policies require signed declarations at submission time

These are **universal patterns** across all incentive policies. The fix is framework-level: composable, config-driven primitives that work through the KPI builder UI.

## Design Principles

1. **Additive, not breaking** — Every new field is optional with null default. Existing configs work identically.
2. **Compose with existing primitives** — Caps, thresholds, frequency limits plug into the existing tier→component→distribution→allocation pipeline at well-defined points.
3. **Configure, don't code** — Every policy rule is expressible through the KPI builder UI, not hardcoded.
4. **Audit-transparent** — When a reward is capped/blocked/threshold-gated, the `explanation` JSON records exactly what happened and why.

#### 3d. New function `applyPerContributorCap()` — add after `resolveComponentAllocations()` definition

```typescript
function applyPerContributorCap(
  allocations: RawAllocation[],
  maxAmountPerPerson: number | null,
): { allocations: RawAllocation[]; totalCapped: number } {
  if (maxAmountPerPerson == null) return { allocations, totalCapped: 0 };

  let totalCapped = 0;
  const capped = allocations.map((a) => {
    if (a.amount > maxAmountPerPerson) {
      totalCapped += a.amount - maxAmountPerPerson;
      return { ...a, amount: maxAmountPerPerson };
    }
    return a;
  });

  return { allocations: capped, totalCapped };
}
```

**Excess is DROPPED, not redistributed.** Cap means ceiling, not pool.

## Task 4: Reward Engine — Threshold Evaluation

### File: `src/lib/kra-kpi/reward-service.ts`

#### 4a. New async function `evaluateThreshold()` — add before `resolveRewards()`

```typescript
async function evaluateThreshold(
  component: RewardComponentRow,
  input: RewardPreviewInput,
  config: RewardConfig,
): Promise<{ passed: boolean; excess?: number; reason?: string }> {
  if (!component.thresholdMode) return { passed: true };

  switch (component.thresholdMode) {
    case "MIN_ACHIEVEMENTS_IN_PERIOD": {
      const count = await prisma.achievement.count({
        where: {
          kpiDefinitionId: config.kpiDefinitionId,
          periodId: config.periodId,
          reportedByUserId: input.reporterUserId,
          state: { in: ["SUBMITTED", "VERIFIED"] },
        },
      });

      if (count < (component.thresholdValue ?? 0)) {
        return {
          passed: false,
          reason: `Only ${count} achievements in period, minimum ${component.thresholdValue} required.`,
        };
      }

      if (component.thresholdBehavior === "SUBTRACT_THRESHOLD") {
        return { passed: true, excess: count - (component.thresholdValue ?? 0) };
      }
      return { passed: true };
    }

    case "MIN_FIELD_VALUE": {
      const fieldValue = component.thresholdFieldKey
        ? coerceNumber(input.achievementFormData[component.thresholdFieldKey])
        : null;

      if (fieldValue == null || fieldValue < (component.thresholdValue ?? 0)) {
        return {
          passed: false,
          reason: `Field ${component.thresholdFieldKey} value ${fieldValue} below threshold ${component.thresholdValue}.`,
        };
      }

      if (component.thresholdBehavior === "SUBTRACT_THRESHOLD") {
        return { passed: true, excess: fieldValue - (component.thresholdValue ?? 0) };
      }
      return { passed: true };
    }

    default:
      return { passed: true };
  }
}
```

    const maxN = config.maxRewardsPerPeriod ?? 1;
    const userIds = contributors
      .map((c) => c.userId)
      .filter((id): id is string => id != null);

    if (userIds.length === 0) {
      return { recurrenceKey, globalReason: null, blockedUserIds: new Set() };
    }

    const rows = await prisma.contributorReward.groupBy({
      by: ["contributorUserId"],
      where: {
        kpiDefinitionId: config.kpiDefinitionId,
        periodId: config.periodId,
        contributorUserId: { in: userIds },
        state: { in: ACTIVE_REWARD_STATES },
        replacedByRewardId: null,

      },
      _count: { id: true },
    });

      rows.map((r) => [r.contributorUserId, r._count.id]),
    );

    const blocked = new Set<string>();
    const userCounts = new Map<string, { existing: number; limit: number }>();
    for (const userId of userIds) {
      const existing = countMap.get(userId) ?? 0;
      userCounts.set(userId, { existing, limit: maxN });
      if (existing >= maxN) {
        blocked.add(userId);
      }

    return { recurrenceKey, globalReason: null, blockedUserIds: blocked, userCounts };

      return { recurrenceKey, globalReason: null, blockedUserIds: new Set() };

      where: {
        kpiDefinitionId: config.kpiDefinitionId,
        recurrenceKey,
        state: { in: ACTIVE_REWARD_STATES },
        replacedByRewardId: null,
        ...(achievementId ? { achievementId: { not: achievementId } } : {}),
      },
    });

    return {
      recurrenceKey,

## Task 11: Cross-KPI Aggregate Cap (at Release Level)

### Why

Nearly every institution says "Faculty total incentive across ALL KPIs capped at ₹5,00,000 per annum." Our engine calculates per-KPI per-achievement, but has no cross-KPI budget envelope.

**Enforced at reward release time** (PENDING → RELEASED), not calculation time. Reasons:
1. Calculation only sees one KPI — cross-KPI queries would be slow and coupled
2. Finance can see full entitlement AND cap enforcement as separate concerns
3. If a reward is revoked, headroom opens up for other pending rewards

### Schema

#### 11a. New model `RewardBudgetCap`

```prisma
model RewardBudgetCap {
  id              String   @id @default(cuid())
  tenantId        String
  periodId        String?            // null = all periods (annual cap)
  benefitTypeId   String?            // null = across all benefit types
  scope           String             // "PER_USER" | "PER_UNIT" | "GLOBAL"
  maxAmount       Float
  isActive        Boolean  @default(true)
  description     String?
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt
  tenant          Tenant   @relation(fields: [tenantId], references: [id], onDelete: Cascade)

  @@unique([tenantId, periodId, benefitTypeId, scope])
  @@index([tenantId, isActive])
}
```

### Implementation

#### 11b. New function `evaluateBudgetCaps()` in `reward-ops-service.ts`

Called during release transition. For each applicable cap:
- **PER_USER**: `SUM(finalAmount)` of RELEASED rewards for this user + period + benefitType
- **PER_UNIT**: same but grouped by `rewardOwnerUnitId`
- **GLOBAL**: same but tenant-wide

If `existingTotal + amountToRelease > cap.maxAmount` → block release with clear reason.

#### 11c. Wire into reward release flow

Before persisting RELEASED state, call `evaluateBudgetCaps()`. Block with reason if exceeded.

## Edge Cases & Invariants

| Case | Behavior |
|------|----------|
| `maxAmount` < `minAmount` | Validation error at save time in KPI builder |
| `maxAmountPerPerson` > `maxAmount` | Allowed — per-person cap may be higher than pool if pool has few people |
| `thresholdValue = 0` | Same as no threshold (0 achievements required = always passes) |
| `maxRewardsPerPeriod = 0` | Validation error (must be ≥ 1) |
| Superseded rewards in frequency count | Excluded — `replacedByRewardId != null` filtered out |
| Cap + recurrence both block | Recurrence checked first (cheaper). If blocked, cap logic skipped |
| Threshold + cap both active | Threshold first → if excess, calculate amount → then cap. Order matters. |
| N_PER_PERIOD with team achievements | Each contributor's count is independent |
| External contributors and frequency | No userId → frequency check skipped. Document limitation. |
| All new fields null | Existing behavior preserved exactly |
| DECLARATION field + readOnly view | Checkbox disabled, shown with checked/unchecked state |
| SUBTRACT_THRESHOLD with excess=0 | multiplier=0 → baseAmount=0. Correct. |
| Budget cap + revoked reward | Revoked rewards excluded from aggregate — headroom opens up |
