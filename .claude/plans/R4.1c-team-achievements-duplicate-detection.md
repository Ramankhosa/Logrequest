# R4.1c — Team Achievements & Duplicate Detection
# ═══════════════════════════════════════════════════════════════════════════════

## Goal

Enable **multi-contributor achievement recording** — reporter adds internal (by UID/name)
and external contributors with roles and credit splits. Add **duplicate detection** at
submission/verification using configurable fields. Migrate from inline
`contributionRole`/`creditPercent` to the new `AchievementContributor` model.

Depends on: R4.1a (ContributorRole, KpiApplicableRole), R4.1b (ExternalContributorTemplate, KpiContributorConfig)

## Locked Decisions

| # | Decision |
|---|----------|
| D1 | Reporter adds all contributors. Verifier validates the list. No consent flow. |
| D2 | One internal user appears at most once per achievement (@@unique on achievementId+userId). PostgreSQL treats NULL != NULL, so multiple external contributors (userId=null) are allowed. |
| D3 | External contributors: data validated against KPI's linked ExternalContributorTemplate. Validation ALWAYS runs when template is linked — if `externalData` is omitted, validate against `{}` to catch missing required fields. |
| D4 | **Credit is system-calculated, never user-input** (superseded by D18+D19). The old `creditSumMode` field on `KpiContributorConfig` is replaced by `creditCapMode` (CAPPED_100 or UNCAPPED). No manual credit sum validation needed — the system guarantees correctness by computing credits automatically. For CAPPED_100: lead role gets fixed credit, others split remainder, total always = 100%. For UNCAPPED: each role gets its `defaultCreditPercent`, total can exceed 100%. |
| D5 | **Contributor requirement depends on KPI configuration**: (a) KPI WITH applicable roles → contributors are **mandatory before submit** (DRAFT can be saved with zero contributors while the reporter builds the list, but submit is blocked by D17 if none exist). For normal requests, reporter must include themselves with their actual role (system auto-calculates credit per D18/D19). For OBO requests (D24), the beneficiary is auto-added, admin is NOT required to be a contributor. Incomplete contributor lists → recommender/approver rejects. (b) KPI WITHOUT applicable roles (simple KPIs) → auto-add reporter (or OBO beneficiary) as sole 100% contributor. No role assignment, no credit calculation — just 100%. |
| D6 | Duplicate detection uses TWO sources: (1) `KpiContributorConfig.duplicateCheckFields` from R4.1b (primary), (2) fields with `marker: "UNIQUE_CHECK"` in achievementFormConfig (fallback). If `duplicateCheckFields` is configured and non-empty, use ONLY those. Otherwise fall back to UNIQUE_CHECK markers. |
| D7 | Duplicate result stored on `achievement.duplicateCheckResult`, shown to verifier as warning. NOT auto-block — verifier decides. |
| D16 | **Duplicate detection scoping**: Exact field matches (DOI, ISBN, patent number etc.) check **cross-period** — globally unique identifiers should never appear twice regardless of period. Fuzzy title matches check **same period only** — recurring KPIs legitimately produce similar titles across periods (monthly workshops, quarterly reports). Each match includes `periodId` and `sameReporter: boolean` so the verifier can judge context. |
| D8 | External contributors default to `isExcludedFromReward = true`. Internal contributors default to `isExcludedFromReward = false`. |
| D9 | Cross-department attribution: DEFERRED to R4.2b dashboard. R4.1c only stores contributor data — does not modify any existing summary/reporting services. |
| D10 | ContributorRole archive: block if role is used in ANY `AchievementContributor` record OR if it's the last applicable role on any KPI. Do NOT auto-remove from KPI applicable lists — the existing `removeContributorRoleFromApplicableKpis()` must NOT be called during archive. Archive only sets `isActive: false` after passing both checks. Add `ROLE_IN_USE_ACHIEVEMENTS` to `kraKpiErrorStatusMap` in `shared.ts` (value: 409). |
| D11 | **ONE creation path**: Extend existing `recordAchievement` to accept optional `contributors[]`. Do NOT create a separate `recordTeamAchievement` function. Same applies to `recordAdditionalAchievement`. |
| D12 | **Achievement.effectiveScore** = base score WITHOUT credit weighting. It remains the canonical achievement-level score used by dashboards and summaries. Per-contributor credit-weighted scores are computed in R4.2b only. This means `calculateEffectiveScore` no longer uses `creditPercent` — just returns `baseScore` directly. The data migration WILL retroactively recalculate all existing effectiveScores to non-credit-weighted values for consistency. Existing tests that assert weighted scores must be updated to assert unweighted scores. |
| D13 | **Dual-read strategy**: ALL view-layer read paths must read from AchievementContributor rows WITH fallback to inline Achievement fields when no contributor rows exist. This includes: `mapAchievementView()` in achievement-service.ts (used by `listAchievements`), and `mapAchievementView` in my-kpi-service.ts. Every Prisma query that feeds these mappers must include `contributors` relation + `duplicateCheckResult` field in its select/include. **Dashboard-service does NOT need dual-read** — it reads `Achievement.effectiveScore` which is a stored column. Since D12's migration (Part B) normalizes all stored effectiveScores to unweighted values, dashboard-service just reads the already-correct value. No contributor-aware logic needed there. |
| D14 | **Migration runs FIRST** (after schema migration), not last. This ensures contributor rows exist before any new code tries to read them. |
| D15 | **Inline fields are read-only shadows** after migration. `Achievement.contributionRole` and `Achievement.creditPercent` are synced FROM the reporter's AchievementContributor row on every contributor CRUD operation. `updateAchievement` ignores inline `contributionRole` when contributor rows exist. See Schema Notes for full sync rules. |
| D17 | **Zero-contributor rule**: An achievement CANNOT be submitted with zero contributors when the KPI has applicable roles. Removing the last contributor in DRAFT is allowed (user may be rebuilding the list), but submit will be blocked. For simple KPIs without roles, the auto-added reporter row always exists so zero-contributor state is impossible. |
| D18 | **Role dropdown is KPI-scoped, credit is AUTO-CALCULATED and NOT editable**: The contributor picker's role dropdown calls `getApplicableRoles(kpiDefinitionId)` and shows ONLY roles configured for that specific KPI, filtered to `isActive = true`. Credit % is **never user-editable** — it is auto-calculated by the system based on the credit cap mode (D19). The credit field is displayed as read-only (greyed out). This prevents gaming and removes verification burden. |
| D19 | **Credit cap mode — two options per KPI** via `KpiContributorConfig.creditCapMode` (new enum field: `CAPPED_100 | UNCAPPED`, default `CAPPED_100`): **CAPPED_100 (default)**: Lead contributors (those with the default/isDefault role) each get their fixed `defaultCreditPercent`. ALL non-lead, reward-eligible contributors split the remainder equally. Excluded contributors (isExcludedFromReward=true) are OUTSIDE the 100% split — they get their role default independently (D23). Total reward-eligible credit = 100%. Rounding: last non-lead gets the remainder to guarantee exact 100% (D20). Credits auto-recalculate every time a contributor is added or removed. **UNCAPPED**: Each contributor gets their role's `defaultCreditPercent` independently regardless of team size, total can exceed 100%. Admin chooses the mode when configuring the KPI's contributor settings in R4.1b. |
| D20 | **CAPPED_100 rounding**: To guarantee total = exactly 100%, the last non-lead reward-eligible contributor gets the remainder: `lastCredit = 100 - leadTotal - (otherCredit × (othersCount - 1))`. This avoids floating-point drift (e.g., 40/9 = 4.44... → 9×4.44 = 39.96, not 40). |
| D21 | **Multiple lead-role contributors in CAPPED_100**: If multiple contributors have the default/lead role (e.g., two PIs on a grant), EACH lead gets their role's `defaultCreditPercent`. `leadTotal = leadCredit × leadCount`. Remainder = `100 - leadTotal`, split among non-leads. If `leadTotal >= 100`, automatically switch to UNCAPPED behavior for this achievement (each role gets its default independently) and log a warning. |
| D22 | **Submit validates contributor roles still applicable**: On submit, for each AchievementContributor with a non-null `contributorRoleId`, verify: (a) role is still in `KpiApplicableRole` for this KPI, AND (b) `contributorRole.isActive = true`. If any role fails, return error with code `CONTRIBUTOR_ROLE_NOT_APPLICABLE` listing the invalid role name(s). This catches admin config changes mid-period. |
| D23 | **Excluded contributors outside CAPPED_100 split**: In CAPPED_100 mode, contributors with `isExcludedFromReward = true` are NOT part of the 100% split. They get their role's `defaultCreditPercent` independently (same as UNCAPPED for that contributor). Only reward-eligible contributors participate in the lead+remainder split. This prevents external contributors from reducing internal members' credit shares. |
| D24 | **On Behalf Of (OBO) requests**: When an admin (TENANT_ADMIN/TENANT_OWNER/SUPERADMIN) or a unit head records an achievement for someone else, it is tagged as an OBO request. Schema: add `isOBO: Boolean @default(false)` and `oboReportedForUserId: String?` to Achievement. The `reportedByUserId` remains the admin/head who entered it. `oboReportedForUserId` is the actual beneficiary. OBO rules: (a) The OBO beneficiary is auto-added as a contributor (with role chosen by admin), NOT the admin who filed it. (b) Admin is NOT required to be in the contributor list. (c) The submit/verification flow works normally — the verifier sees "Filed on behalf of Dr. X by Admin Y." (d) In My Contributions, the achievement appears under `oboReportedForUserId`'s view, not the admin's. (e) Only admins and unit heads (for their unit members) can create OBO requests. |
| D25 | **My Contributions visibility**: Contributors can only see achievements in state SUBMITTED, RECOMMENDED, or VERIFIED. DRAFT achievements are excluded — the reporter may still be editing or may delete the draft. This prevents premature visibility of incomplete data. |
| D26 | **Retroactive duplicate flag**: When achievement B is verified and has `duplicateCheckResult.hasDuplicates = true`, the system updates the matched achievement A's `duplicateCheckResult` to add a `retroactiveMatches` array with B's info. This is informational only — does NOT change A's state or block anything. Allows audit trails to show both sides of a duplicate pair. |

### AchievementContributor
```prisma
model AchievementContributor {
  id                    String                    @id @default(cuid())
  achievementId         String
  type                  ContributorType           @default(INTERNAL)
  // Internal
  userId                String?
  // External
  externalName          String?
  externalAffiliation   String?
  externalScope         ExternalContributorScope?
  externalData          Json?                     // validated against template
  // Common
  contributorRoleId     String?                   // null for simple KPIs without applicable roles (D5b)
  creditPercent         Float
  isExcludedFromReward  Boolean                   @default(false)
  rewardRedistribution  String?                   // "RETURN_TO_POOL" | "SPLIT_INTERNAL" | "NO_REDISTRIBUTION"
  disputeStatus         String?                   // null | "DISPUTED" — contributor can flag issue (D7b)
  disputeNote           String?                   // reason for dispute
  disputedAt            DateTime?
  note                  String?
  addedByUserId         String
  createdAt             DateTime                  @default(now())
  updatedAt             DateTime                  @updatedAt
  achievement           Achievement               @relation(fields: [achievementId], references: [id], onDelete: Cascade)
  user                  User?                     @relation("ContributorUser", fields: [userId], references: [id])
  contributorRole       ContributorRole?          @relation(fields: [contributorRoleId], references: [id], onDelete: Restrict)
  addedBy               User                      @relation("ContributorAddedBy", fields: [addedByUserId], references: [id])

  @@unique([achievementId, userId])
  @@index([achievementId])
  @@index([userId])
}
```

### D15: Inline Field Sync Rules (NEW)
After migration, `Achievement.contributionRole` and `Achievement.creditPercent` are **read-only shadows** synced FROM contributor rows:
1. **On create** (recordAchievement): If contributors[] provided, sync reporter's role name + credit to inline fields. If auto-added (D5), sync 100% + default role name.
2. **On contributor CRUD** (add/remove/update credit): After any change to AchievementContributor rows, re-sync the reporter's row (userId = reportedByUserId) back to `Achievement.contributionRole` and `Achievement.creditPercent`. If reporter has no contributor row, set both to null.
3. **On updateAchievement**: When contributor rows exist, IGNORE `contributionRole` from input — do not update the inline field. When NO contributor rows exist (pre-migration edge case), keep existing inline logic.
4. **Schema**: `updateAchievementSchema` still accepts `contributionRole` for old clients. It is silently ignored when contributor rows exist. No validation error — just a no-op.

## CRITICAL: Existing Code That Must Change

### 1. `src/lib/kra-kpi/achievement-service.ts` (~2100 lines)

#### a. `calculateEffectiveScore` (line 217)
**Current**: `return creditPercent != null ? baseScore * (creditPercent / 100) : baseScore;`
**Change to (D12)**: `return baseScore;`
This is the key change. effectiveScore is now always the base score. Credit weighting moves to R4.2b.

**Migration**: The data migration (step 3 in build order) will retroactively recalculate ALL existing effectiveScores to non-credit-weighted values. This ensures consistency — one formula everywhere, dashboards read correct values immediately.

**Change in place** — modify `calculateEffectiveScore` directly:
```typescript
function calculateEffectiveScore(baseScore: number | null): number | null {
  return baseScore;
}
```
Remove the `creditPercent` parameter entirely. All call sites pass only `baseScore`.

**Test updates**: Any existing tests asserting `effectiveScore = baseScore * creditPercent / 100` must be updated to assert `effectiveScore = baseScore` (or `computedScore` / `stageCompletionScore` as appropriate).

**IMPORTANT — submissionTrail.scoreAtAction**: Historical `scoreAtAction` values in `submissionTrail` entries are NOT migrated. They preserve the score at the time of each action (audit trail integrity). After migration, `achievement.effectiveScore` may differ from the last trail entry's `scoreAtAction`. This is correct behavior. The UI should display trail scores as "Score at time of action" and NOT compare them to the current effectiveScore. Do NOT attempt to "fix" this discrepancy.

**PRODUCT DECISION — Historical Dashboard Impact**: The D12 migration is an intentional product behavior change. By recalculating all stored `effectiveScore` values to remove credit weighting, historical dashboards and period summaries WILL show different numbers after migration. This is by design — the old credit-weighted scores were an implementation detail that is being replaced by the cleaner model where per-contributor credit scores move to R4.2b. Acceptance criterion: after migration, all dashboards show unweighted base scores. Any period that was already CLOSED/ARCHIVED will also reflect the new scores.

```typescript
// STEP 2: Calculate credits based on creditCapMode (D19, D20, D21, D23)
function calculateCredits(
  contributors: Array<ContributorInput & { isExcludedFromReward?: boolean }>,
  resolvedRoles: Map<string, { name: string; defaultCreditPercent: number; isDefault: boolean }>,
  creditCapMode: "CAPPED_100" | "UNCAPPED",
): Array<{ index: number; creditPercent: number }> {

  // UNCAPPED: simple — each contributor gets their role's defaultCreditPercent
  if (creditCapMode === "UNCAPPED") {
    return contributors.map((c, i) => ({
      index: i,
      creditPercent: resolvedRoles.get(c.contributorRoleId)!.defaultCreditPercent,
    }));
  }

  // ── CAPPED_100 logic ──

  // Solo contributor logic (D27):
  // - Solo with LEAD role (isDefault) → 100%. Sole author, sole PI — full credit.
  // - Solo with NON-LEAD role → role's defaultCreditPercent (e.g., Co-Author 15%).
  //   Low credit signals incomplete data to recommender.
  // NOTE: For simple KPIs (D5b, no applicable roles), the auto-add path
  // creates a contributor with creditPercent=100 directly — it does NOT
  // go through calculateCredits. So this code only runs for role-based KPIs.
  if (contributors.length === 1) {
    const role = resolvedRoles.get(contributors[0].contributorRoleId)!;
    return [{
      index: 0,
      creditPercent: role.isDefault ? 100 : role.defaultCreditPercent,
    }];
  }

  // Classify contributors into 3 groups:
  // 1. Leads (isDefault role AND reward-eligible)
  // 2. Non-lead reward-eligible (participate in 100% split)
  // 3. Excluded (isExcludedFromReward=true — get role default OUTSIDE the split, D23)
  const leads: number[] = [];       // indices
  const nonLeads: number[] = [];    // indices
  const excluded: number[] = [];    // indices

  contributors.forEach((c, i) => {
    const role = resolvedRoles.get(c.contributorRoleId)!;
    if (c.isExcludedFromReward) {
      excluded.push(i);
    } else if (role.isDefault) {
      leads.push(i);
    } else {
      nonLeads.push(i);
    }
  });

  const result: Array<{ index: number; creditPercent: number }> = [];

  // D23: Excluded contributors get their role default, outside the split
  for (const idx of excluded) {
    result.push({
      index: idx,
      creditPercent: resolvedRoles.get(contributors[idx].contributorRoleId)!.defaultCreditPercent,
    });
  }

  // No leads found among reward-eligible → fallback to UNCAPPED for reward-eligible
  if (leads.length === 0) {
    for (const idx of nonLeads) {
      result.push({
        index: idx,
        creditPercent: resolvedRoles.get(contributors[idx].contributorRoleId)!.defaultCreditPercent,
      });
    }
    return result;
  }

  // D21: Multiple leads — each gets their role's defaultCreditPercent
  const leadCredit = resolvedRoles.get(contributors[leads[0]].contributorRoleId)!.defaultCreditPercent;
  const leadTotal = leadCredit * leads.length;

  // D21: If leadTotal >= 100, auto-switch to UNCAPPED for this achievement
  if (leadTotal >= 100) {
    for (const idx of [...leads, ...nonLeads]) {
      result.push({
        index: idx,
        creditPercent: resolvedRoles.get(contributors[idx].contributorRoleId)!.defaultCreditPercent,
      });
    }
    return result;
  }

  // Assign lead credits
  for (const idx of leads) {
    result.push({ index: idx, creditPercent: leadCredit });
  }

  // Split remainder among non-lead reward-eligible contributors
  if (nonLeads.length > 0) {
    const remainder = 100 - leadTotal;
    const baseCredit = Math.floor((remainder / nonLeads.length) * 100) / 100; // floor to 2 decimals

    for (let i = 0; i < nonLeads.length; i++) {
      if (i < nonLeads.length - 1) {
        result.push({ index: nonLeads[i], creditPercent: baseCredit });
      } else {
        // D20: Last non-lead gets the remainder to guarantee exact 100%
        const assignedSoFar = leadTotal + baseCredit * (nonLeads.length - 1);
        const lastCredit = Math.round((100 - assignedSoFar) * 100) / 100;
        result.push({ index: nonLeads[i], creditPercent: lastCredit });
      }
    }
  }

  return result;
}
```

```typescript
  excludeAchievementId?: string,
): Promise<DuplicateCheckResult> {
  if (!formData && !achievementTitle) return { checked: false, hasDuplicates: false, matches: [] };

  // 1. Determine which fields to check (D6: two sources)
  // Note: formData may be null for title-only achievements — field checks will be skipped,
  // but fuzzy title matching (step 4) still runs using achievementTitle.
  const fieldsToCheck: string[] = [];

  // Primary: KpiContributorConfig.duplicateCheckFields (from R4.1b)
  const config = await getEffectiveConfig(kpiId, tenantId);
  const configFields = config.duplicateCheckFields;
  const hasConfigFields = Array.isArray(configFields) && configFields.length > 0;

  if (hasConfigFields) {
    fieldsToCheck.push(...configFields);
  } else {
    // Fallback: UNIQUE_CHECK markers from achievementFormConfig
    const kpi = await prisma.kpiDefinition.findFirst({
      where: { id: kpiId, kraDefinition: { tenantId } },
      select: { achievementFormConfig: true },
    });
    if (!kpi) return { checked: false, hasDuplicates: false, matches: [] };

    // CORRECT TYPE: AchievementFormConfig = { templateKey?, fields: [...] }
    const formConfig = kpi.achievementFormConfig as AchievementFormConfig | null;
    if (formConfig?.fields) {
      const markedFields = formConfig.fields.filter((f: AchievementFieldConfig) => f.marker === "UNIQUE_CHECK");
      fieldsToCheck.push(...markedFields.map((f: AchievementFieldConfig) => f.key));
    }
  }

  const matches: DuplicateMatch[] = [];

  // If no field-based checks AND no title for fuzzy match, nothing to do
  if (fieldsToCheck.length === 0 && !achievementTitle) {
    return { checked: true, hasDuplicates: false, matches: [] };
  }

  // 2. Fetch candidate achievements (D16: cross-period for exact, same-period for fuzzy)
  // Fetch ALL non-DRAFT achievements for this KPI across all periods (exact match needs cross-period)
  const candidates = await prisma.achievement.findMany({
    where: {
      kpiDefinitionId: kpiId,
      tenantId,
      state: { not: "DRAFT" },
      ...(excludeAchievementId ? { id: { not: excludeAchievementId } } : {}),
    },
    select: {
      id: true, state: true, title: true, periodId: true,
      achievementFormData: true, reportedByUserId: true,
    },
  });

  // 3. For each field, check for exact matches (skip if formData is null)
  if (formData && fieldsToCheck.length > 0)
  for (const fieldKey of fieldsToCheck) {
    const value = formData[fieldKey];
    if (value == null || value === "") continue;
    const stringValue = String(value).trim().toLowerCase();

    for (const candidate of candidates) {
      const candidateFormData = candidate.achievementFormData as Record<string, unknown> | null;
      if (!candidateFormData) continue;
      const candidateValue = candidateFormData[fieldKey];
      if (candidateValue == null) continue;
      const candidateString = String(candidateValue).trim().toLowerCase();

      if (candidateString === stringValue) {
        // Avoid duplicate matches for same achievement
        if (matches.some((m) => m.achievementId === candidate.id && m.matchedField === fieldKey)) continue;
        const reporter = await prisma.user.findUnique({
          where: { id: candidate.reportedByUserId },
          select: { firstName: true, lastName: true },
        });
        matches.push({
          achievementId: candidate.id,
          matchedField: fieldKey,
          matchedValue: String(candidateValue),
          reportedByName: reporter ? `${reporter.firstName} ${reporter.lastName}` : "Unknown",
          reportedByUserId: candidate.reportedByUserId,
          sameReporter: candidate.reportedByUserId === reporterUserId,
          achievementState: candidate.state,
          achievementTitle: candidate.title,
          periodId: candidate.periodId,
          samePeriod: candidate.periodId === periodId,
          similarity: "EXACT",
        });
      }
    }
  }

  // 4. Secondary: fuzzy title match (D16: SAME PERIOD ONLY)
  // Recurring KPIs (monthly workshops, quarterly reports) legitimately produce similar titles
  // across periods, so fuzzy matching only checks within the current period.
  // Use achievement.title (top-level Achievement field, NOT formData) for fuzzy matching
  if (matches.length === 0) {
    const titleValue = achievementTitle;
    if (titleValue && typeof titleValue === "string" && titleValue.length > 10) {
      const titleLower = titleValue.toLowerCase();
      const samePeriodCandidates = candidates.filter((c) => c.periodId === periodId);
      for (const candidate of samePeriodCandidates) {
        if (!candidate.title) continue;
        const candidateTitle = candidate.title.toLowerCase();
        const words1 = new Set(titleLower.split(/\s+/).filter((w) => w.length > 3));
        const words2 = new Set(candidateTitle.split(/\s+/).filter((w) => w.length > 3));
        if (words1.size === 0 || words2.size === 0) continue;
        const intersection = [...words1].filter((w) => words2.has(w)).length;
        const similarity = intersection / Math.max(words1.size, words2.size);
        if (similarity > 0.7) {
          const reporter = await prisma.user.findUnique({
            where: { id: candidate.reportedByUserId },
            select: { firstName: true, lastName: true },
          });
          matches.push({
            achievementId: candidate.id,
            matchedField: "title",
            matchedValue: candidate.title,
            reportedByName: reporter ? `${reporter.firstName} ${reporter.lastName}` : "Unknown",
            reportedByUserId: candidate.reportedByUserId,
            sameReporter: candidate.reportedByUserId === reporterUserId,
            achievementState: candidate.state,
            achievementTitle: candidate.title,
            periodId: candidate.periodId,
            samePeriod: true, // D16: fuzzy always same-period (filtered above)
            similarity: "FUZZY",
          });
        }
      }
    }
  }

  return { checked: true, hasDuplicates: matches.length > 0, matches };
}
```
